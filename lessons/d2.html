2.1 Configure and verify VLANs (normal range) spanning multiple switches

A VLAN is a Layer 2 broadcast domain carved out of a switch (or a set of switches). Ports in VLAN 10 only flood broadcasts, unknown unicasts and multicasts to other ports in VLAN 10. Each VLAN is normally one IP subnet, so traffic between VLANs must be routed. On the exam you need to build VLANs, put ports in them, carry them between switches (topic 2.2) and route between them (2.1.c).

2.1.b The default VLAN (VLAN 1)

Out of the box every switch port is in VLAN 1 (and in dynamic auto mode, see 2.2), the native VLAN on trunks is VLAN 1, and control protocols such as CDP, VTP and PAgP are sent in VLAN 1 on trunks (DTP on an 802.1Q trunk uses the native VLAN, which is also VLAN 1 by default). VLAN 1 cannot be deleted. The interface Vlan1 SVI exists by default (shut down) and is often used for management on small switches.

Security best practice, which Cisco and the exam both reward:

  • Move all user ports out of VLAN 1 into named VLANs.
  • Use a dedicated management VLAN (for example VLAN 99) for the switch SVI instead of VLAN 1.
  • Change the trunk native VLAN to an unused VLAN that carries no users.
  • Put unused ports in an unused "parking" VLAN and shut them down.

2.1.a Access ports (data and voice)

An access port belongs to one data VLAN. Frames enter and leave it untagged; the switch associates the frame with the access VLAN internally. Hard-code access mode so the port never negotiates a trunk:

SW1(config)# interface range fastethernet0/1 - 2
SW1(config-if-range)# switchport mode access
SW1(config-if-range)# switchport access vlan 10
SW1(config-if-range)# exit
SW1(config)# interface fastethernet0/3
SW1(config-if)# switchport mode access
SW1(config-if)# switchport access vlan 20

Voice VLAN

An IP phone usually sits between the switch and a PC: switch port to the phone's network port, PC into the phone's PC port. One cable now carries two kinds of traffic. Cisco handles this with a voice VLAN (Cisco calls it an auxiliary VLAN):

  • switchport access vlan 10 sets the data VLAN. The PC's frames cross the link untagged.
  • switchport voice vlan 30 sets the voice VLAN. The phone sends its own voice frames tagged with 802.1Q VID 30 (with CoS 5 in the PCP bits).
  • The switch tells the phone which VLAN to use with CDP (Cisco phones) or LLDP-MED (network policy TLV, multivendor phones). The phone does not need to be configured by hand.
  • The port is still an access port, not a trunk. show interfaces trunk does not list it. It does appear under both VLAN 10 and VLAN 30 in show vlan brief.
SW1(config)# interface fastethernet0/5
SW1(config-if)# switchport mode access
SW1(config-if)# switchport access vlan 10
SW1(config-if)# switchport voice vlan 30

2.1.c Inter-VLAN connectivity

Hosts in different VLANs are in different subnets, so a Layer 3 device must route between them. The default gateway of each host is that Layer 3 device's address in the host's subnet. There are three CCNA methods.

Method 1: Router-on-a-stick (ROAS)

One router physical interface connects to a switch trunk. The router creates one subinterface per VLAN, each with encapsulation dot1q <vlan-id> and an IP address that acts as the default gateway for that VLAN. Frames arrive tagged; the router strips the tag, routes, and re-tags with the egress subinterface's VLAN.

R1(config)# interface gigabitethernet0/0
R1(config-if)# no ip address
R1(config-if)# no shutdown
! Subinterfaces inherit the physical interface's up/down state
R1(config-if)# interface gigabitethernet0/0.10
R1(config-subif)# encapsulation dot1q 10
R1(config-subif)# ip address 192.168.10.1 255.255.255.0
R1(config-subif)# interface gigabitethernet0/0.20
R1(config-subif)# encapsulation dot1q 20
R1(config-subif)# ip address 192.168.20.1 255.255.255.0
R1(config-subif)# interface gigabitethernet0/0.99
R1(config-subif)# encapsulation dot1q 99 native
R1(config-subif)# ip address 192.168.99.1 255.255.255.0

SW1(config)# interface gigabitethernet0/1
SW1(config-if)# switchport mode trunk
SW1(config-if)# switchport trunk native vlan 99
SW1(config-if)# switchport trunk allowed vlan 10,20,99
  • The subinterface number (.10) is only a label. The encapsulation dot1q VLAN ID is what matters. Matching them is convention, and mismatching them is a classic exam distractor.
  • You must configure encapsulation dot1q before IOS accepts an IP address on a subinterface.
  • The native VLAN: either use a subinterface with encapsulation dot1q 99 native, or put the native VLAN's IP address on the physical interface itself. Do not do both. The router's native VLAN must match the switch trunk's native VLAN.
  • The router port has no DTP. The switch side must be switchport mode trunk (a dynamic mode never forms a trunk with a router).
  • Drawback: all inter-VLAN traffic crosses one link twice (in and out), so the link is a bottleneck and a single point of failure.

Method 3: Routed ports

On a Layer 3 switch, no switchport turns a physical port into a routed port: it belongs to no VLAN, runs no STP or DTP, and takes an IP address directly, exactly like a router interface. Use it for point-to-point links between a Layer 3 switch and a router or another Layer 3 switch (for example core uplinks running OSPF).

DSW1(config)# interface gigabitethernet1/0/24
DSW1(config-if)# no switchport
DSW1(config-if)# ip address 10.0.0.1 255.255.255.252
DSW1(config-if)# no shutdown

DSW1# show interfaces gigabitethernet1/0/24 switchport

On the CCNA, a Layer 2 access switch such as the 2960 does not route between VLANs. It normally has one management SVI and uses ip default-gateway (not a default route) to reach other subnets. (Some 2960 models running the LAN Base image can do limited static routing between SVIs, but that is outside the exam.)

2.2 Configure and verify interswitch connectivity

When a VLAN spans several switches, the links between them must carry many VLANs at once. A trunk does this by tagging each frame with its VLAN ID. On the CCNA the trunking standard is IEEE 802.1Q; Cisco's old proprietary ISL is gone from current switches and from the blueprint.

2.2.b 802.1Q tagging

802.1Q inserts a 4-byte tag between the source MAC address and the EtherType/Length field. Because the frame changes, the sender recalculates the FCS. The maximum Ethernet frame grows from 1518 to 1522 bytes (a "baby giant" that 802.1Q-aware switches accept).

TPID (Tag Protocol Identifier), 16 bits
Always 0x8100 for 802.1Q. Identifies the frame as tagged.
PCP (Priority Code Point), 3 bits
The 802.1p Class of Service (CoS) value 0 to 7. Voice is usually CoS 5. This is the Layer 2 QoS marking covered again in 4.7.
DEI (Drop Eligible Indicator), 1 bit
Marks a frame as eligible to drop under congestion. Formerly called CFI (Canonical Format Indicator).
VID (VLAN Identifier), 12 bits
VLAN ID. 2 to the power 12 = 4096 values; 0 and 4095 are reserved, so 1 to 4094 are usable.

2.2.a Trunk ports and DTP

A Cisco switch port's Layer 2 mode is set with switchport mode:

ModeBehavior
accessAlways access, whatever the neighbor does. Never trunks.
trunkAlways trunk. Sends DTP to invite the neighbor to trunk too (unless nonegotiate is set).
dynamic desirableActively sends DTP and becomes a trunk if the neighbor is trunk, desirable or auto.
dynamic autoPassive: becomes a trunk only if the neighbor is trunk or desirable. Default on current Catalyst switches (2960, 3650, 9200, 9300).

DTP (Dynamic Trunking Protocol) is Cisco proprietary. It negotiates whether the link trunks (and, on old ISL-capable switches, which encapsulation to use).

"Mismatch" means one side tags and the other does not: only the native VLAN (untagged) happens to work, everything else is dropped. Avoid it.

Exam trap: two brand-new Catalyst switches cabled together (both dynamic auto) do not form a trunk. They form an access link in VLAN 1. Old 3550-era switches defaulted to dynamic desirable, which is why some older material says otherwise; answer with dynamic auto for current Cisco switches.

switchport nonegotiate

switchport nonegotiate stops the port from sending DTP frames. It is accepted only on a port in access or trunk mode. A trunk with nonegotiate still trunks, but its neighbor must also be statically set to trunk: a neighbor in dynamic auto or dynamic desirable hears no DTP and stays access. Best practice is switchport mode trunk + switchport nonegotiate on every switch-to-switch trunk and switchport mode access on every edge port, so an attacker cannot negotiate a trunk (switch spoofing).

switchport trunk encapsulation

Switches that support both ISL and 802.1Q (for example Catalyst 3560/3750, and the 3560 model in Packet Tracer) default to switchport trunk encapsulation negotiate and reject switchport mode trunk with "Command rejected: An interface whose trunk encapsulation is "Auto" can not be configured to "trunk" mode." Enter switchport trunk encapsulation dot1q first. Switches that support only 802.1Q (2960, 9200, 9300) do not need it, and on many of them the command does not exist.

Configuring a trunk

SW1(config)# interface gigabitethernet0/1
! Next line only on ISL-capable models (3560/3750)
SW1(config-if)# switchport trunk encapsulation dot1q
SW1(config-if)# switchport mode trunk
SW1(config-if)# switchport nonegotiate
SW1(config-if)# switchport trunk native vlan 99
SW1(config-if)# switchport trunk allowed vlan 10,20,30,99

Allowed VLAN list

By default a trunk allows VLANs 1 to 4094. You can restrict it, which also limits flooding and the scope of each VLAN's spanning tree.

CommandResult
switchport trunk allowed vlan 10,20Replaces the whole list with exactly 10 and 20.
switchport trunk allowed vlan add 30Adds 30 to the existing list.
switchport trunk allowed vlan remove 20Removes 20 from the existing list.

2.2.c Native VLAN

The native VLAN is the one VLAN whose frames cross an 802.1Q trunk untagged. A frame received untagged on a trunk is placed in the native VLAN. The default native VLAN is 1. It exists for backward compatibility with devices that do not understand tags.

  • Both ends must use the same native VLAN. It is set per trunk with switchport trunk native vlan X.
  • Mismatch symptoms: the trunk still comes up, but untagged frames sent in SW1's native VLAN arrive in SW2's native VLAN. The two VLANs are silently bridged, and normal connectivity in both breaks. CDP detects it and logs: 
    %CDP-4-NATIVE_VLAN_MISMATCH: Native VLAN mismatch discovered on GigabitEthernet0/1 (99), with SW2 GigabitEthernet0/1 (1).
    Rapid PVST+ also notices (its per-VLAN BPDUs carry the sender's VLAN) and blocks the port for the two VLANs involved as "PVID inconsistent", for example %SPANTREE-2-BLOCK_PVID_LOCAL: Blocking GigabitEthernet0/1 on VLAN0099. Inconsistent local vlan.
  • Security best practice: set the native VLAN to an unused VLAN (for example 99 or 999) with no access ports and no SVI, the same on both ends. This defeats the double-tagging VLAN-hopping attack, which only works when the attacker's access VLAN equals the trunk's native VLAN.
  • Tagging the native VLAN: the global command vlan dot1q tag native makes the switch tag native-VLAN frames on its trunks too, so user data never crosses a trunk untagged.

Router-on-a-stick and the native VLAN

On a router subinterface, encapsulation dot1q 99 native tells the router to send and expect VLAN 99 untagged. It must match the switch's native VLAN.

Tip: VTP (VLAN Trunking Protocol) is not on the v1.1 blueprint. Know only that it can synchronize VLANs from a server switch to clients, and that many networks run every switch in VTP transparent mode (or VTP off) so each switch keeps its own VLAN list. In transparent mode VLAN configuration is also saved in the running config.

2.3 Configure and verify Layer 2 discovery protocols (CDP and LLDP)

CDP and LLDP let a device announce who it is to its directly connected neighbors. They run at Layer 2, so they work even before IP is configured, and they never cross a router or a switch (each device consumes them, it does not forward them). They are the fastest way to map a network you did not build, and the exam uses their output to ask "which port connects to what".

What they advertise

Both carry TLVs (type-length-value fields). The common ones:

  • Device ID (hostname) and the sending port ID
  • Management/Layer 3 address(es)
  • Capabilities (router, switch/bridge, phone, host, WLAN AP)
  • Platform/model and software version (CDP "Platform" and "Version"; LLDP "System Description")

  • LLDP: system name, system description, port description, plus optional organizationally specific TLVs: 802.1 (such as port VLAN ID), 802.3 (such as MAC/PHY configuration) and LLDP-MED (network policy, power)

2.4 Configure and verify Layer 2/Layer 3 EtherChannel (LACP)

Connect two switches with two parallel links and STP blocks one of them, so you pay for bandwidth you cannot use. EtherChannel bundles 2 to 8 physical links into one logical link (a port-channel). STP sees one link with one cost, so nothing blocks; traffic is load-shared across members; if a member fails, traffic moves to the others without an STP reconvergence.

Member requirements

Every member port, on both switches, must match on:

  • Speed and duplex
  • Switchport mode (all access or all trunk) and, for access, the same access VLAN
  • For trunks: the same allowed VLAN list and the same native VLAN
  • Layer 2 vs Layer 3 (all switchports, or all no switchport)
  • One channel-group per port; do not mix LACP and PAgP in one group

A port that does not match is suspended (flag s) or left stand-alone (I), and the switch logs something like %EC-5-CANNOT_BUNDLE2: Gi0/2 is not compatible with Gi0/1 and will be suspended (vlan mask is different). Best practice: configure members with interface range, then put them in the channel group, and make later changes on the port-channel interface, which pushes them to all members.

Limits: PAgP and static channels bundle up to 8 active links. LACP can have up to 16 ports configured in a group: 8 active and up to 8 hot-standby (flag H) that replace a failed active member. LACP system priority and port priority both default to 32768 (lower is preferred) and decide which ports are active when more than 8 are configured.

Load balancing

EtherChannel does not split one flow over several links. The switch hashes fields of each frame (MAC addresses, IP addresses, or Layer 4 ports, depending on the method) and the hash picks a member link, so all frames of one conversation take the same link and stay in order. The default on many Catalyst switches is src-mac. If most traffic goes to one router MAC or one server, a MAC-based hash can push nearly everything onto one link; src-dst-ip usually spreads better.

2.5 Interpret basic operation of Rapid PVST+

Redundant Layer 2 links create loops. Ethernet frames have no TTL, so a broadcast in a loop circulates forever (a broadcast storm), MAC tables flap between ports, and hosts receive duplicate frames. Spanning Tree Protocol prevents this by building a loop-free tree: it picks one root switch, keeps the best path from every switch to the root, and puts every other redundant port into a non-forwarding state. If an active link fails, a blocked port takes over.

Bridge ID and the extended system ID

Every switch has a Bridge ID (BID) per VLAN: an 8-byte value made of a 2-byte priority field and the switch's 6-byte base MAC address. With PVST+ and Rapid PVST+, the 16-bit priority field is split:

  • 4 bits of configurable priority, so the value you set must be a multiple of 4096 (0, 4096, 8192 ... 61440). Default 32768.
  • 12 bits of extended system ID, which IOS sets to the VLAN number.

So the priority shown for VLAN 10 on a default switch is 32768 + 10 = 32778. The same switch shows 32769 in VLAN 1 and 32788 in VLAN 20. Lower BID is better: compare priority first, then MAC address.

2.5.a Root bridge, root port, designated port and the election

Step 1: elect the root bridge

All switches start by claiming to be root and sending BPDUs (hello every 2 s) listing their own BID as Root ID. When a switch hears a superior (lower) Root ID, it stops claiming and relays the better one. The switch with the lowest BID becomes root for that VLAN. All of the root's (working) ports are designated ports and forward.

Step 2: each non-root switch picks one root port

The root port is the port with the best path to the root. Tie-breakers, in order:

  1. Lowest root path cost: the cost the neighbor advertises in its BPDU plus the cost of the local port the BPDU arrived on.
  2. Lowest sender (neighbor) Bridge ID.
  3. Lowest sender port priority (default 128).
  4. Lowest sender port number.

Tie-breakers 3 and 4 use the neighbor's port ID (the one in the received BPDU). They matter only with parallel links to the same neighbor.

Step 3: each segment (link) gets one designated port

On every link, the switch that offers the best path to the root through that link owns the designated port: lowest advertised root path cost, then lowest BID, then lowest port priority, then lowest port number. The designated port forwards.

Step 4: everything else is blocked

Any port that is neither root nor designated becomes an alternate port (or backup, see 2.5.b) and discards.

Worked example

  1. Root: SW1 has priority 24586 (24576 + 10, set with root primary); the others have 32778. Lowest priority wins: SW1 is root. Its Gi0/1 and Gi0/2 are designated.
  2. SW2 root port: via Gi0/1 the cost is 0 + 4 = 4; via Gi0/2 (through SW3) it is 4 + 4 = 8. Gi0/1 wins. SW3 likewise picks its Gi0/1 (cost 4).
  3. SW2 to SW3 link: both switches advertise root cost 4 onto it. Tie, so compare BIDs: same priority 32778, SW2's MAC 0022... is lower than SW3's 0033.... SW2 Gi0/2 is designated.
  4. SW3 Gi0/2 is neither root nor designated: alternate, discarding. If SW3 Gi0/1 fails, Gi0/2 becomes the root port almost immediately (RSTP).

Variation 1 (cost wins over a direct link): replace the SW1 to SW3 link with FastEthernet (cost 19). SW3's direct path now costs 19, while the path through SW2 costs 4 + 4 = 8. SW3's Gi0/2 (toward SW2) becomes its root port, SW2's Gi0/2 is still designated (it advertises 4, SW3 would advertise 8), and SW3's FastEthernet port toward SW1 becomes alternate (SW1's end is designated, as every root port is). The direct link to the root is the one that blocks.

Variation 2 (neighbor port ID tie-breaker): SW4 connects to root SW1 with two parallel gigabit links, SW4 Gi0/1 to SW1 Gi0/2 and SW4 Gi0/2 to SW1 Gi0/1. Root cost ties (4 and 4), sender BID ties (both SW1), sender port priority ties (128). Lowest sender port number wins: the BPDU from SW1 Gi0/1 (port 128.25) beats SW1 Gi0/2 (128.26), so SW4's root port is its Gi0/2, the port cabled to SW1 Gi0/1. Answering "Gi0/1 because it is SW4's lowest port" is the trap.

  • root primary sets the priority to 24576 if that is enough to make this switch root.   • root secondary sets 28672, which beats default switches (32768) but loses to the primary.
  • Port priority: 0 to 240 in steps of 16, default 128. Lower is preferred. Changing it on a switch influences the neighbor's root-port choice (because the neighbor uses the sender port ID).
  • Port cost: lowering the cost on a local port makes it more attractive as this switch's root port.

802.1D timers (sent by the root, used by all): hello 2 s, max age 20 s, forward delay 15 s. A port moving to forwarding spends 15 s listening plus 15 s learning = 30 s. An indirect failure adds up to 20 s of max age first, so up to 50 s.

RSTP is faster because:

  • Every switch sends its own BPDUs every hello (2 s), and a neighbor is declared lost after 3 missed hellos (6 s), instead of waiting for max age.
  • An alternate port takes over as root port immediately when the root port fails.
  • On point-to-point links, designated ports use a proposal/agreement handshake: the upstream switch proposes to forward, the downstream switch puts its other non-edge ports in sync (discarding) and agrees, and the port goes straight to forwarding without timers. This ripples down the tree in well under a second.
  • Edge ports (PortFast) go to forwarding at once and do not cause topology changes.

2.5.c PortFast

A port connected to a PC, printer, server or AP has no loop risk, so waiting through discarding and learning only delays DHCP and logins. PortFast makes the port an edge port: it goes straight to forwarding when the link comes up, and its up/down events do not generate topology changes (which would flush MAC tables network-wide).

! Per interface
SW1(config)# interface fastethernet0/1
SW1(config-if)# spanning-tree portfast
%Warning: portfast should only be enabled on ports connected to a single
 host. Connecting hubs, concentrators, switches, bridges, etc... to this
 interface  when portfast is enabled, can cause temporary bridging loops.
 Use with CAUTION

! Globally: every access (non-trunking) port becomes edge
SW1(config)# spanning-tree portfast default

! Trunk to a server or hypervisor that does not run STP
SW1(config-if)# spanning-tree portfast trunk

! Newer IOS XE syntax adds the keyword "edge":

SW1(config-if)# spanning-tree portfast edge

PortFast does not disable STP on the port: the port still sends BPDUs, and if it receives one it loses edge status and behaves as a normal STP port. That is why it is paired with BPDU guard.

BPDU filter: global and interface behave differently

  • Global spanning-tree portfast bpdufilter default (IOS XE: portfast edge bpdufilter default): applies only to ports that are operationally PortFast. Those ports still send a few BPDUs when the link comes up, then stop sending. If such a port ever receives a BPDU, it loses PortFast and BPDU filtering and runs normal STP. This is relatively safe.
  • Interface spanning-tree bpdufilter enable: the port neither sends nor processes received BPDUs, whether or not PortFast is set. It effectively disables STP on that port. A loop through it will not be detected. Use only when you are certain (for example toward another administrative domain).
  • If interface BPDU filter and BPDU guard are both on a port, the filter wins: the port never processes the BPDU, so guard never triggers.

Loop guard

SW3(config)# interface gigabitethernet0/2

%SPANTREE-2-LOOPGUARD_BLOCK: Loop guard blocking port GigabitEthernet0/2 on VLAN0010.

An alternate port stays discarding only because it keeps hearing BPDUs from the designated port. If a fiber strand fails so BPDUs stop arriving but the link stays up (a unidirectional link), the alternate port would age out the information, become designated and forward, creating a loop. Loop guard instead moves it to loop-inconsistent (still discarding). Use it on root and alternate ports, typically on uplinks between switches. Root guard and loop guard cannot both be enabled on the same port.

Exam trap: match the feature to its state. BPDU guard = err-disabled (needs manual or errdisable recovery). Root guard = root-inconsistent, loop guard = loop-inconsistent (both recover by themselves). Root guard reacts to a superior BPDU; loop guard reacts to the absence of BPDUs; BPDU guard reacts to any BPDU.

2.6 Cisco wireless architectures and AP modes

Topic 1.11 covered RF, channels and SSIDs. This topic is about how access points (APs) are managed and where client traffic goes. The exam expects you to name each architecture, say where the controller lives, and pick the AP mode that fits a job.

Autonomous APs

An autonomous AP is a self-contained device: it runs its own IOS, is configured one by one (CLI or web GUI), and bridges wireless clients straight onto the wired network. Each SSID maps to a VLAN on the AP, so an AP serving several SSIDs connects to a trunk port. There is no central RF management, so channel and power planning, security policy and roaming are per AP. Fine for a home or very small office, painful at scale. A management IP in a management VLAN is needed on each AP.

Lightweight APs and the split-MAC architecture

A lightweight AP (LAP) cannot work on its own. It discovers a Wireless LAN Controller (WLC), downloads its configuration (and software) from it, and from then on the 802.11 MAC functions are split between them: split-MAC.

AP (real-time functions)WLC (management functions)

CAPWAP

The AP and WLC talk over CAPWAP (Control And Provisioning of Wireless Access Points, RFC 5415), a standard based on Cisco's earlier LWAPP. CAPWAP builds two tunnels between the AP's IP address and the WLC's management interface:

  • Control tunnel: UDP 5246. Configuration, AP management, keepalives. Always encrypted with DTLS.
  • Data tunnel: UDP 5247. Client frames encapsulated between AP and WLC. DTLS encryption of data is optional (off by default on Cisco controllers; turned on as "data link encryption" when needed).

Because CAPWAP runs over UDP/IP, the AP and WLC can be in different subnets, across a routed network or a WAN. The AP finds a WLC by: a Layer 3 broadcast on its own subnet, DHCP option 43 (WLC IPv4 address in the AP's DHCP offer), a DNS lookup of CISCO-CAPWAP-CONTROLLER.<localdomain>, previously learned controllers, or statically configured primary/secondary/tertiary controller names.

Recap

  • Autonomous AP: standalone, configured individually, trunk for multiple SSIDs/VLANs.
  • Lightweight AP + WLC = split-MAC: real-time 802.11 on the AP, management (auth, roaming, RRM, policy) on the WLC.
  • CAPWAP: control UDP 5246 (DTLS-encrypted), data UDP 5247 (encryption optional). Discovery: broadcast, DHCP option 43, DNS, previously joined.
  • Deployments: centralized, cloud (Meraki, 9800-CL), embedded (on a Catalyst 9000 switch), Mobility Express/EWC (on an AP), FlexConnect for branches.
  • AP modes: local (default), FlexConnect, monitor, rogue detector, sniffer, SE-Connect, bridge/mesh, Flex+Bridge.

The console port gives CLI access with no IP configuration, so it is how you set up a new device or recover one that is unreachable. Telnet and SSH (VTY lines)

Remote CLI sessions use virtual terminal (VTY) lines, usually line vty 0 4 or 0 15. The device needs an IP address reachable from the admin (and on a Layer 2 switch, an SVI plus ip default-gateway). Telnet sends everything, including the password, in clear text, so anyone capturing packets reads it. Use SSH and restrict the lines:

R1(config)# line vty 0 15
R1(config-line)# login local
R1(config-line)# transport input ssh

! a Telnet attempt gets "Password required, but none set" and is closed

HTTP and HTTPS

Many IOS/IOS XE devices (and every WLC) have a web interface. ip http server enables the clear-text HTTP server on TCP 80; ip http secure-server enables HTTPS on TCP 443 with a self-signed or installed certificate. Best practice: no ip http server, keep only HTTPS if you need a GUI, and authenticate it with ip http authentication local (or AAA). The Catalyst 9800 and AireOS WLC GUIs are reached over HTTPS.

AAA: TACACS+ and RADIUS

Local usernames on every device do not scale and are hard to audit. AAA (authentication, authorization, accounting; concepts in 5.8) centralizes logins on a server such as Cisco ISE. The device is the AAA client and talks to the server with TACACS+ or RADIUS.

The method list is tried in order; local is used only if the server does not respond. If the server answers "reject", the login fails and the local database is not consulted. After aaa new-model, the default login method applies to all lines unless overridden, so configure it before you close your session.

Cloud-managed devices

Cisco Meraki switches, APs and security appliances are managed from the Meraki dashboard, a web portal in the cloud. Each device connects outbound to the cloud over an encrypted tunnel and pulls its configuration. You manage everything from a browser (HTTPS) without console or SSH sessions to individual devices; zero-touch deployment means a device configured in the dashboard just needs power and an internet path. Management is out-of-band: user traffic does not pass through the cloud, and devices keep forwarding with their last configuration if the cloud is unreachable. Some Catalyst 9000 switches can also be monitored or managed from the Meraki dashboard.

In-band versus out-of-band management

In-band
Management traffic (SSH, SNMP, HTTPS) uses the same network that carries user data, for example an SVI in a management VLAN. Cheap, but if the production network breaks, you lose management access with it.
Out-of-band (OOB)
A separate path used only for management: the console port (often via a terminal/console server), or a dedicated management Ethernet port on its own network (Catalyst 9000 GigabitEthernet0/0 in the Mgmt-vrf, a WLC service port). Survives production outages and is easier to secure.

The four things every WLAN needs

  1. An identity: WLAN ID, profile name and SSID.
