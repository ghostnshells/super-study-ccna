3.1 Interpret the components of a routing table

Domain 3 is 25% of the exam, and almost every question in it starts from the same artifact: the output of show ip route. If you can read every field of that output without hesitation, 3.2 (forwarding decisions), 3.3 (static routes) and 3.4 (OSPF) become much easier, because they all end up as lines in this table.

The routing table (the RIB, routing information base) is the router's list of the best path it knows to each destination prefix. Many sources feed it: connected interfaces, static routes, and each running routing protocol. Each source offers candidate routes. The router installs only the best candidate for each prefix, and the installed set is what you see in show ip route. Packets are then forwarded from that table (in practice from CEF, which is built from it; see 3.2).

3.1.b Prefix

The prefix is the destination network the route describes, for example 10.20.0.0 in 10.20.0.0/16. It is always the network address (host bits zero), never a host address, except for /32 host routes. The prefix together with its length is the route's identity: 10.1.0.0/16 and 10.1.0.0/24 are two different routes and can both be in the table at the same time.

The table is sorted numerically by prefix and grouped under classful headings (see 3.1.c). The default route 0.0.0.0/0 is listed first.

3.1.c Network mask

IOS shows the mask in prefix-length notation (/24). Two header styles appear, and both are just formatting, not routes:

172.16.0.0/24 is subnetted, 2 subnets
All routes inside the classful network 172.16.0.0 (a Class B) use the same mask, /24. The mask is printed once on the header, so the child lines show 172.16.5.0 with no prefix length.
10.0.0.0/8 is variably subnetted, 8 subnets, 4 masks
The classful network 10.0.0.0/8 holds 8 child routes using 4 different masks (/30, /32, /16 and /24 here). Each child line then carries its own prefix length. Count them in the example: 10.1.12.0/30, 10.1.12.1/32, 10.1.13.0/30, 10.1.13.1/32, 10.20.0.0/16, 10.30.1.0/24, 10.40.1.0/24 and 10.50.0.0/16.

Because every routed interface produces a /n connected route and a /32 local route, almost every classful network that contains a router interface shows as "variably subnetted". That is why 192.168.1.0/24 (one C route and one L route) has "2 subnets, 2 masks".

Local (L) routes

Since IOS 15, each interface address gets an L route with a /32 mask: L 10.1.12.1/32 is directly connected, GigabitEthernet0/0. It tells the router "this exact address is me", so packets to it are processed locally (pings to the router, SSH, routing protocol packets) instead of being forwarded. A loopback configured with a /32 mask shows only the C route (C 1.1.1.1 is directly connected, Loopback0) because the connected route is already a /32.

Exam trap: The exam may ask how many routes a table holds or which mask a destination uses. Header lines ("is subnetted", "is variably subnetted") are not routes. And a child line under an "is subnetted" header has the mask from the header, even though the line itself shows no /n.

3.1.d Next hop

The next hop is the IP address of the neighboring router that the packet is handed to, shown after via. The outgoing interface follows the age at the end of the line. Variations you must recognize:

  • Dynamic route: [110/3] via 10.1.12.2, 00:14:07, GigabitEthernet0/0: next hop, age, outgoing interface.
  • Static route with next hop only: S 172.16.5.0 [1/0] via 10.1.13.2. No interface is shown. The router finds the interface by a second (recursive) lookup of 10.1.13.2, which matches the connected route 10.1.13.0/30 on Gi0/1.
  • Fully specified static: S 172.16.6.0 [1/0] via 10.1.13.2, GigabitEthernet0/1: both next hop and interface were configured.
  • Static route to an interface only: S 172.16.7.0 is directly connected, GigabitEthernet0/1. It looks like a connected route but the code is S. show ip route 172.16.7.0 reports it as known via "static", distance 1, metric 0 (connected).
  • Connected and local routes: no next hop; the destination is on the wire of that interface.
  • Equal-cost paths: a second line indented under the first, with another via (see 3.2).

The age (00:14:07, or 1d02h for older routes) is how long ago the route was installed or last updated. A route that keeps resetting to a few seconds old in OSPF or EIGRP is a sign of instability (flapping).

3.1.e Administrative distance

Administrative distance (AD) is the first number in brackets: [110/3]. It rates how trustworthy a route source is. When two different sources (for example OSPF and EIGRP) offer the exact same prefix and length, the router installs the one with the lower AD. AD is local to the router; it is never advertised to neighbors.

The metric is the second number in brackets: [110/3]. It is the routing protocol's own cost to reach the destination. It is only meaningful within one protocol: an OSPF cost of 3 and an EIGRP metric of 3072 cannot be compared, which is exactly why AD exists.

3.1.g Gateway of last resort

The line above the routes tells you whether the router has a default route and where it points:

  • Gateway of last resort is 203.0.113.1 to network 0.0.0.0: a default route is installed; packets that match nothing more specific go to 203.0.113.1.
  • Gateway of last resort is not set: no default route. Packets that match no route are dropped (3.2).

The default route itself is the 0.0.0.0/0 line, flagged with * (candidate default). It can come from a static route (S*), from OSPF (O*E2 when a neighbor uses default-information originate), from EIGRP (D* or D*EX), or from DHCP. If several sources offer 0.0.0.0/0, normal AD rules decide which one is installed.

Tip: On the exam, when a question asks where a packet to an unknown destination goes, look at the gateway of last resort line first. If it says "not set", the answer is "dropped", no matter how many other routes exist.

3.2 How a router makes a forwarding decision by default

Two different decisions are hidden in this topic, and most exam mistakes come from mixing them up:

  1. Route selection (building the table). Which candidate route for a given prefix gets installed? Decided by administrative distance (between sources) and then metric (within one protocol). This happens in the control plane whenever routing information changes.
  2. Forwarding lookup (using the table). For one packet, which installed route matches its destination? Decided by longest prefix match. This happens for every packet.

So the default behavior, in the order a packet experiences it: longest prefix match first picks the route; AD and metric already did their work earlier, deciding which routes are in the table at all.

3.2.a Longest prefix match

When a packet arrives, the router compares its destination IP with every route in the table. A route matches if the first n bits of the destination equal the first n bits of the route's prefix, where n is the prefix length. Several routes can match. The router uses the matching route with the longest prefix length (the most specific route), regardless of its AD or metric.

The default route: /0 is always the shortest match

A default route, 0.0.0.0/0 (or ::/0 for IPv6), has zero bits to compare, so it matches every destination. Because it is the shortest possible match, it is used only when nothing else matches. That is why it is called the gateway of last resort.

When nothing matches

If no route matches and there is no default route, the router drops the packet and sends an ICMP Destination Unreachable message back to the source address. From a Cisco router, a ping in that situation typically shows U.U.U: IOS rate-limits ICMP unreachables (by default one every 500 ms), so every other reply is a timeout (.). A plain ..... instead usually means the packet was forwarded but nothing came back, for example a missing return route on a later router.

3.2.b Administrative distance

AD is used only when two or more route sources offer the same prefix with the same length. Each routing protocol picks its own best route, then offers it to the routing table. The routing table manager installs the offer with the lowest AD. The losing route is not deleted from its protocol (it stays in the OSPF LSDB or the EIGRP topology table), so if the winner disappears, the next best source is installed automatically. Floating static routes (3.3.d) are built on exactly this behavior.

Example: suppose R5 also learned 172.16.40.0/24 from EIGRP via 10.9.9.3. OSPF offers [110/30] via 10.9.9.2; EIGRP offers [90/3328] via 10.9.9.3. EIGRP wins on AD, so the table now shows:

Remember: The order of the three tools: longest prefix match chooses among routes in the table; AD chooses which source installs a given prefix/length; metric chooses the best path within one protocol. A question that compares a /24 and a /16 is an LPM question, not an AD question.

3.2.c Routing protocol metric

Within one routing protocol, the route with the lowest metric for a prefix wins and is offered to the table. OSPF compares total cost; EIGRP compares its composite metric; RIP compares hop count. (OSPF also has an internal preference order before cost: intra-area beats inter-area, which beats external type 1, which beats external type 2. In single-area OSPF all routes are intra-area, so cost decides.)

Equal-cost multipath (ECMP)

If a protocol finds two or more paths with the same best metric, it installs all of them, up to its maximum-paths limit. On IOS the default for OSPF and EIGRP is 4; the configurable maximum depends on platform (commonly 16 or 32). The routing table shows the extra paths as indented lines under the first:

O        172.16.0.0/16 [110/20] via 10.9.9.6, 00:03:12, GigabitEthernet0/0
                       [110/20] via 10.9.9.2, 00:03:12, GigabitEthernet0/0
R5(config)# router ospf 1
R5(config-router)# maximum-paths 2
! maximum-paths 1 disables load sharing: only one path is installed

CEF shares traffic across equal paths per destination by default (it hashes source and destination IP), so one flow stays on one path and packets arrive in order. Two static routes to the same prefix with the same AD also produce ECMP.

Metric is never compared between protocols. An EIGRP metric of 3328 is not "worse" than an OSPF cost of 30; they are different units, and AD decides between them.

Background: CEF, the FIB and the adjacency table

Cisco routers do not search the routing table for every packet. Cisco Express Forwarding (CEF, enabled by default with ip cef) precomputes two tables from the control plane:

  • FIB (forwarding information base): a copy of the routing table optimized for longest-match lookups, with recursive next hops already resolved. show ip cef.
  • Adjacency table: for each next hop, the ready-made Layer 2 header (destination MAC from ARP, source MAC, EtherType). show adjacency.
R5# show ip cef 172.16.40.77
172.16.40.64/26
  nexthop 10.9.9.4 GigabitEthernet0/0
R5# show ip cef 172.16.100.1
172.16.0.0/16
  nexthop 10.9.9.2 GigabitEthernet0/0
  nexthop 10.9.9.6 GigabitEthernet0/0

The forwarding result is the same as the routing table logic (longest match); CEF just does it faster, in hardware on switches and most routers. For the CCNA, know that the RIB is the control-plane table and the FIB plus adjacency table are the data-plane tables built from it.

Recap

  • Per packet, the router uses the matching route with the longest prefix length. AD and metric are not compared across different prefix lengths.
  • AD decides only between sources offering the identical prefix/length; the lowest AD is installed, the loser waits in its protocol's database.
  • Metric decides within one protocol; equal metrics give ECMP up to maximum-paths (IOS default 4 for OSPF and EIGRP).
  • The default route (/0) matches everything and is used last. With no match and no default, the packet is dropped and an ICMP unreachable goes to the source (ping shows U.U.U).
  • CEF forwards from the FIB (prefixes, resolved next hops) and adjacency table (prebuilt Layer 2 headers), derived from the routing table.

3.3 Configure and verify IPv4 and IPv6 static routing

A static route is a route you type in. It never changes on its own, uses no CPU or bandwidth for updates, and reveals nothing to neighbors. It also never adapts: if the path fails silently, the static route keeps sending traffic into the failure. In practice statics are used for default routes toward an ISP, stub sites with one exit, specific overrides, and backups (floating statics). The exam expects you to configure all four kinds named in the outline (default, network, host, floating) for both IPv4 and IPv6, and to read and troubleshoot them.

IPv4 syntax: three ways to say where to send it

R1(config)# ip route prefix mask {next-hop-ip | exit-interface [next-hop-ip]} [distance] [permanent] [name text]
FormExampleShows in the table as
Next hop only (recursive)ip route 192.168.2.0 255.255.255.0 10.0.12.2S 192.168.2.0/24 [1/0] via 10.0.12.2
Exit interface onlyip route 192.168.2.0 255.255.255.0 GigabitEthernet0/0S 192.168.2.0/24 is directly connected, GigabitEthernet0/0
Fully specified (interface + next hop)ip route 192.168.2.0 255.255.255.0 GigabitEthernet0/0 10.0.12.2S 192.168.2.0/24 [1/0] via 10.0.12.2, GigabitEthernet0/0

The mask is always a dotted-decimal subnet mask (not a wildcard, not /n). The prefix must be the network address for that mask: ip route 192.168.3.5 255.255.255.0 10.0.12.2 is rejected with %Inconsistent address and mask.

Next hop only: recursive lookup

With a next-hop IP, the router needs a second lookup to find the outgoing interface: it looks up 10.0.12.2 in its own table, matches the connected route 10.0.12.0/30 on Gi0/0, and forwards there. This is called a recursive route. It also means the next hop does not have to be directly connected: ip route 172.16.0.0 255.255.0.0 10.5.5.5 works if some other route covers 10.5.5.5, and IOS resolves it in as many steps as needed. On Ethernet, the router ARPs only for the next hop, which is exactly what you want.

Exit interface only: fine on serial, a problem on Ethernet

An interface-only static says "the destination is directly reachable out this interface". On a point-to-point serial link (HDLC or PPP) that is true enough, because there is only one device on the other end and no ARP is needed. On Ethernet, the router has no next-hop address, so it treats every destination in the prefix as if it were on the local wire and ARPs for each final destination address. That works only if the neighbor router answers those ARPs on behalf of the remote hosts (proxy ARP, enabled by default on IOS interfaces but often disabled by security policy). The result is either a large ARP cache and extra CPU (one ARP entry per remote destination; terrible for a default route) or, with proxy ARP off, no connectivity at all. Cisco recommends specifying the next hop (or both) on Ethernet (Configure a Next Hop IP Address for Static Routes).

Fully specified

Interface plus next hop avoids both problems: no recursion is needed to find the interface, and ARP is done only for the next hop. It is also required for IPv6 link-local next hops (below).

Exam trap: An interface-only static route displays as "is directly connected", but its code is S and its AD is still 1 (show ip route on the prefix shows "Known via static, distance 1, metric 0 (connected)"). It is not a connected route with AD 0.

When is a static route actually installed?

  • Next-hop form: only while the next hop is resolvable through another route in the table (normally a connected subnet). If 10.0.12.0/30 disappears because Gi0/0 goes down, the static route is withdrawn.
  • Interface form: only while that interface is up/up.
  • Fully specified: only while the interface is up.
  • Its AD must also be the lowest offer for that exact prefix (that is what makes a floating static wait).
  • The permanent keyword keeps the route installed even if the interface goes down. Rarely a good idea; know that it exists.

The important consequence: a static route only notices failures the router itself can see. If R1 and R2 connect through a switch and R2 dies, R1's Gi0/0 stays up, 10.0.12.2 still looks resolvable, and the static route stays in the table, black-holing traffic. (IP SLA tracking fixes this but is beyond CCNA scope.)

3.3.a Default route

A default route matches every destination with zero bits (0.0.0.0/0) and is used when nothing more specific matches. Typical uses: a branch or stub router with a single upstream, and an edge router toward an ISP.

R1(config)# ip route 0.0.0.0 0.0.0.0 203.0.113.1
R1(config)# end
R1# show ip route | include Gateway|0.0.0.0
Gateway of last resort is 203.0.113.1 to network 0.0.0.0
S*    0.0.0.0/0 [1/0] via 203.0.113.1

The * marks it as the candidate default, and the gateway of last resort line is set. To share a static default with OSPF neighbors, the edge router adds default-information originate under router ospf (3.4); neighbors see it as O*E2.

Do not confuse ip route 0.0.0.0 0.0.0.0 with ip default-gateway. The latter is for a device that is not routing (a Layer 2 switch's management interface, or a router with no ip routing). A routing device ignores ip default-gateway.

3.3.b Network route

A network route points to a specific subnet (anything between /1 and /31). It is the most common static route:

R1(config)# ip route 192.168.2.0 255.255.255.0 10.0.12.2
R1(config)# ip route 172.16.0.0 255.255.0.0 GigabitEthernet0/1 10.0.13.2

A short prefix can act as a summary: one static for 172.16.0.0/16 covers every 172.16.x.x subnet behind that neighbor.

3.3.c Host route

A host route matches exactly one address: mask 255.255.255.255 (/32) for IPv4, /128 for IPv6. Because it is the longest possible prefix, it always wins longest prefix match. Typical uses: steer traffic for one server along a different path (through a firewall, over a different link), or reach a peer's loopback.

R1(config)# ip route 192.168.3.10 255.255.255.255 10.0.12.2
R1# show ip route static | begin 192.168.3
      192.168.3.0/24 is variably subnetted, 2 subnets, 2 masks
S        192.168.3.0/24 [1/0] via 10.0.13.2, GigabitEthernet0/1
S        192.168.3.10/32 [1/0] via 10.0.12.2

Traffic to 192.168.3.10 goes via R2 (10.0.12.2); traffic to every other 192.168.3.x host goes straight to R3. Note that connected interfaces already create /32 local (L) routes; a static host route is something you add for a remote address.

3.3.d Floating static route

A floating static route is a backup static route configured with an AD higher than the primary route's AD. While the primary exists, the floating route loses the AD comparison and is not installed (it "floats" above the table). If the primary is withdrawn, the floating static is installed automatically; when the primary returns, it takes over again.

! Primary path: OSPF (AD 110) over Gi0/0. Backup: static over Gi0/1.
R1(config)# ip route 192.168.2.0 255.255.255.0 10.0.21.2 130
  • Over OSPF (110), use any AD from 111 to 254. Over EIGRP internal (90), use 91 or more (but note an EIGRP external route is 170). Values like 130, 200 or 250 are common.
  • For a static backing up another static, give the primary the default AD 1 and the backup a higher one, for example 5. The primary must be withdrawable (next hop or interface can fail) or the backup never floats in.
  • AD 255 means "never install": the route is useless.

While the primary is active, show ip route does not show the floating route at all. Check the configuration (show running-config | include ip route) to see it. After a failover it appears with its configured AD in brackets: S 192.168.2.0/24 [130/0] via 10.0.21.2.

Exam trap: If the "floating" static has an AD lower than the dynamic route (for example 100 under OSPF's 110, or the default 1), it is not floating: it becomes the primary path and OSPF's route for that prefix is never installed. A classic exam exhibit shows a static with AD 100 and asks why traffic uses the backup link.

Tip: Failover is only as fast as the primary route's withdrawal. If the link goes down on R1's own interface, OSPF drops the neighbor immediately. If the failure is somewhere R1 cannot see (through a switch), OSPF waits for the dead timer (40 s by default) before the route is removed and the floating static appears.

Why a link-local next hop needs the interface

Every IPv6 interface has a link-local address (FE80::/10), and the same link-local address can exist on every link (R2 in the lab below uses FE80::2 on two interfaces, which is legal). A link-local address alone is ambiguous: the router cannot tell which link it lives on. So when the next hop is link-local, you must give the exit interface as well. Typing ipv6 route 2001:DB8:3:3::/64 FE80::2 without an interface is rejected (IOS reports that an interface has to be specified for a link-local next hop). Link-local next hops are popular because they do not change if global addressing is renumbered, and they are what dynamic protocols use anyway.

A global unicast next hop alone is fine: the router resolves it recursively, exactly like IPv4. As in IPv4, an interface-only route on Ethernet is a poor choice: there is no proxy ARP in IPv6, so the router would try Neighbor Discovery for every destination on the remote prefix.

3.4 Configure and verify single-area OSPFv2

OSPF (Open Shortest Path First, version 2 for IPv4, RFC 2328) is the routing protocol the CCNA tests hands-on. The blueprint limits you to a single area, but within that area you need everything: how adjacencies form, the two network types, DR/BDR election, router ID, configuration both ways, and reading every verification command. Expect exhibit questions that show show ip ospf neighbor or show ip ospf interface output and ask why two routers are not neighbors or who the DR is.

How link-state routing works

A distance-vector protocol (RIP) tells neighbors "I can reach X at distance N". A link-state protocol instead has every router describe its own links (its interfaces, their subnets, their costs, and which neighbors are on them) and flood that description to every router in the area. Each router then holds the same map and computes its own best paths.

  1. Neighbors: routers discover each other with Hello packets and form adjacencies.
  2. Flooding: each router originates LSAs (link-state advertisements) describing itself and floods them to the area. Every router stores every LSA in its LSDB (link-state database). All routers in an area must have identical LSDBs.
  3. SPF: each router runs Dijkstra's shortest path first algorithm over the LSDB, with itself as the root, to build a shortest-path tree. The best routes go into the routing table with AD 110 and the total cost as the metric.
  4. Change: when a link changes, only the affected LSA is reflooded and SPF reruns. There are no periodic full updates; LSAs are refreshed every 30 minutes and expire at 60 minutes (MaxAge) if not refreshed.

Areas

An area is a group of routers that share one LSDB. Area 0 is the backbone; in multi-area designs every other area must attach to it, through ABRs (area border routers). Areas keep the LSDB and SPF work small in big networks. A single-area design simply puts every interface in one area, normally area 0. Area IDs are 32-bit and may be written as a number (0) or dotted decimal (0.0.0.0); both mean the same area.

OSPF packets and addresses

OSPF runs directly over IP as IP protocol 89 (not TCP or UDP). It has five packet types: Hello (discover and keep neighbors), DBD (database description: a list of LSA headers), LSR (link-state request), LSU (link-state update: carries LSAs) and LSAck. Two multicast addresses:

  • 224.0.0.5 (AllSPFRouters): every OSPF router listens. Hellos go here, and the DR floods updates here.
  • 224.0.0.6 (AllDRouters): only the DR and BDR listen. DROTHERs send their updates here.

The reference topology

Basic configuration: network commands

R1(config)# interface Loopback0
R1(config-if)# ip address 1.1.1.1 255.255.255.255

  • network address wildcard area id: enables OSPF on every interface whose primary IP address matches the address/wildcard pair, and puts that interface in the area.

How network command matching works

The wildcard is an inverse mask: a 0 bit means "must match", a 1 bit means "ignore". IOS compares each interface's IP address (not its subnet) against the statement. If it matches, OSPF is enabled on the interface; the router then sends hellos there and advertises the interface's real subnet and mask, whatever range the network command covered.

network 10.0.123.1 0.0.0.0 area 0Only the interface whose address is exactly 10.0.123.1 (precise, popular in production)
network 10.0.0.0 0.255.255.255 area 0Every interface in 10.0.0.0/8

Alternative: interface configuration

Instead of network statements you can enable OSPF directly on each interface. The result is identical; it is more explicit and avoids wildcard errors. Interface configuration takes precedence if both methods cover an interface.

R1(config)# router ospf 1
R1(config-router)# router-id 1.1.1.1
R1(config-router)# exit
R1(config)# interface Loopback0
R1(config-if)# ip ospf 1 area 0
R1(config-if)# interface GigabitEthernet0/0
R1(config-if)# ip ospf 1 area 0
R1(config-if)# interface GigabitEthernet0/1
R1(config-if)# ip ospf 1 area 0

show ip ospf interface tells you which method enabled an interface: "Attached via Network Statement" or "Attached via Interface Enable". show ip protocols lists network statements under "Routing for Networks" and interface-enabled interfaces under "Routing on Interfaces Configured Explicitly".

Passive interfaces

A passive interface still has its subnet advertised into OSPF, but OSPF sends no hellos on it and ignores hellos received there, so no neighbor can form. Use it on every LAN where no OSPF router should exist: it saves overhead and stops a rogue device from forming an adjacency and injecting routes.

R4(config)# router ospf 1
R4(config-router)# passive-interface GigabitEthernet0/1
! Or make everything passive and enable only the transit links:
R4(config-router)# passive-interface default
R4(config-router)# no passive-interface GigabitEthernet0/0

Loopbacks never send hellos anyway, so they do not need to be made passive.

Exam trap: "Passive" does not mean "not advertised". The passive LAN's subnet still appears in every other router's table. If a question says a LAN is missing from other routers, passive-interface is not the cause; a missing network statement is. If two routers will not become neighbors over a link, passive-interface on that link is a prime suspect.

Advertising a default route

R2(config)# ip route 0.0.0.0 0.0.0.0 203.0.113.1
R2(config)# router ospf 1
R2(config-router)# default-information originate

R2 becomes an ASBR and floods a type 5 LSA for 0.0.0.0/0. Other routers install it as O*E2 0.0.0.0/0 [110/1] (external type 2, metric 1 by default) and their gateway of last resort points toward R2. Without the always keyword, R2 advertises the default only while it has a default route in its own table; if the static default is withdrawn, the OSPF default is withdrawn too. default-information originate always advertises it unconditionally.

OSPF interface cost = reference bandwidth / interface bandwidth, rounded down, minimum 1. The default reference is 100 Mbps (10^8 bps).

With the default reference, every link of 100 Mbps or faster costs 1, so OSPF cannot prefer a 10 Gbps path over a FastEthernet one. Three ways to influence cost:

  • auto-cost reference-bandwidth mbps under router ospf: changes the formula for every interface. Set the same value on every router in the area, or costs become inconsistent. IOS warns: % OSPF: Reference bandwidth is changed. Please ensure reference bandwidth is consistent across all routers.
  • ip ospf cost 1-65535 on an interface: sets that interface's cost directly, overriding the formula.
  • bandwidth kbps on an interface: changes the bandwidth value OSPF (and EIGRP and QoS) use in calculations. It does not change the physical speed. Mostly used on serial links.

Cost is counted on outgoing interfaces only: a route's metric is the sum of the costs of each router's exit interface along the path, including the destination subnet's interface on the last router. R1's route to R3's LAN 192.168.3.0/24 = R1 Gi0/0 (1) + R3 Gi0/1 (1) = 2. To R2's loopback = 1 + 1 (loopback cost) = 2.

OSPF installs up to 4 equal-cost paths by default (maximum-paths, see 3.2).

3.4.a Neighbor adjacencies

Every hello interval an OSPF router multicasts a Hello on each OSPF-enabled, non-passive interface. If it hears nothing from a neighbor for the dead interval, it declares the neighbor down. Defaults:

Network typeHelloDead
Broadcast (Ethernet default)10 s40 s
Point-to-point (HDLC/PPP serial default, or configured)10 s40 s
Non-broadcast (NBMA) and point-to-multipoint30 s120 s

A Hello contains the sender's router ID, area ID, hello and dead intervals, network mask, authentication data, option flags (including the stub-area flag), router priority, the current DR and BDR, and the list of neighbor RIDs it has heard from on that link. Modern Ethernet links between two routers (routed uplinks, WAN handoffs) are often configured as point-to-point for exactly these reasons:

Exam trap: If one side of a link is broadcast and the other point-to-point, the hello and dead timers still match (10/40), so the neighbor can come up, sometimes even to Full. But the broadcast side expects a DR and a type 2 LSA, the point-to-point side does not, and SPF cannot build a consistent path over the link: routes through it are missing. Always check show ip ospf interface on both ends.

3.4.c Broadcast (DR/BDR selection)

On a multiaccess segment with n routers, a full mesh of adjacencies would need n(n-1)/2 adjacencies and every change would be flooded by every router to every other. OSPF instead elects a designated router (DR) and a backup designated router (BDR). Every other router (a DROTHER) forms a full adjacency only with the DR and BDR; DROTHERs stay in 2-Way with each other. With 10 routers that is 17 adjacencies instead of 45.

  • A DROTHER sends LSUs to 224.0.0.6 (heard by DR and BDR only).
  • The DR refloods them to 224.0.0.5 (every OSPF router on the segment).
  • The DR originates the segment's type 2 network LSA.
  • The BDR is fully adjacent with everyone and takes over immediately if the DR fails.

Election rules

  1. Only routers with interface priority 1 to 255 are candidates. Priority 0 means never DR or BDR. Default priority is 1. Set with ip ospf priority 0-255 on the interface.
  2. Highest priority wins. On a tie, the highest router ID wins (not the highest interface IP).
  3. The BDR is elected first among non-DR candidates, then the DR. In practice: the best router becomes DR, the second best BDR.
  4. The election is non-preemptive. Once a DR and BDR exist, a newly arriving router with a higher priority does not take over. It becomes DR only when the current DR and BDR fail, or after the OSPF process is reset on the segment. One exception: setting priority 0 on the current DR or BDR makes it ineligible at once, and the other routers rerun the election.
  5. When the DR fails, the BDR is promoted to DR and a new BDR is elected. When the old DR returns, it becomes a DROTHER.
  6. When an interface comes up and sees no DR, it waits the wait timer (equal to the dead interval, 40 s) before electing, so other routers have a chance to be heard. This is why the first router powered on often becomes DR regardless of priority: it is alone for 40 seconds.

The DR is a role on a segment (an interface), not on a router. R1 can be DR on one LAN, DROTHER on another and have no role at all on its point-to-point links.

R3# show ip ospf neighbor

1.1.1.1         200   FULL/DR         00:00:37    10.0.0.1        GigabitEthernet0/0

Exam trap: The neighbor table never shows the local router's own role. To know whether R3 itself is DR, BDR or DROTHER, look at show ip ospf interface ("State DROTHER") or infer it: if R3 lists both a DR and a BDR among its neighbors, R3 is neither.

3.4.d Router ID

The router ID (RID) is a 32-bit number written like an IPv4 address that uniquely identifies the router in OSPF: it appears in hellos, it is the Link ID of the router's type 1 LSA, it breaks DR election ties, and it decides the master in ExStart. It does not have to be an address on the router, or even a reachable one. IOS chooses it when the OSPF process starts, in this order:

  1. The router-id a.b.c.d command under router ospf.
  2. Otherwise, the highest IPv4 address on any up loopback interface.
  3. Otherwise, the highest IPv4 address on any up non-loopback interface.

The interface does not need to be enabled for OSPF to be used for the RID. Example: R5 has Lo0 1.1.1.1, Lo1 11.11.11.11 and Gi0/0 203.0.113.2 and no router-id command: its RID is 11.11.11.11 (any up loopback beats any physical interface, even though 203.0.113.2 is numerically higher). If no interface has an IPv4 address in an up state, the process cannot start (%OSPF-4-NORTRID).

When the RID changes

The RID is stable: adding a higher loopback, or even typing a new router-id, does not change a running process on classic IOS. IOS tells you so:

R1(config-router)# router-id 1.1.1.1
% OSPF: Reload or use "clear ip ospf process" command, for this to take effect
R1(config-router)# end
R1# clear ip ospf process
Reset ALL OSPF processes? [no]: yes

clear ip ospf process (or a reload) restarts OSPF, drops every adjacency on the router and rebuilds them with the new RID. Do it in a maintenance window. (Recent IOS XE releases, from 17.13.1a, apply a new router-id immediately and reset the adjacencies themselves; the CCNA answer is still "clear the process or reload".)

Best practice is to set the RID explicitly, usually equal to a loopback address that is also advertised, so the RID is predictable and also reachable for troubleshooting.

Remember: RID order = router-id command, highest up loopback, highest up physical interface. Chosen at process start; changed only by clear ip ospf process or reload. RIDs must be unique within the OSPF domain.

Troubleshooting OSPF adjacencies

A systematic order works best: (1) is the interface up/up with the right IP and mask (show ip interface brief); (2) is OSPF running on it and in which area (show ip ospf interface brief); (3) is it passive (show ip protocols); (4) do timers, network type and mask agree on both ends (show ip ospf interface); (5) what state is the neighbor in (show ip ospf neighbor); (6) if still unclear, debug ip ospf adj or debug ip ospf hello (and undebug all afterwards). Log messages differ slightly between IOS releases; the ones below are typical.

Fault 1: mismatched hello/dead timers

R2 has ip ospf hello-interval 5 on Gi0/0, which also sets its dead interval to 20. R1 and R2 no longer list each other; R2 disappears from R1's neighbor table after the dead timer expires.

R1# debug ip ospf hello
OSPF: Rcv hello from 2.2.2.2 area 0 from GigabitEthernet0/0 10.0.123.2
OSPF: Mismatched hello parameters from 10.0.123.2
OSPF: Dead R 20 C 40, Hello R 5 C 10  Mask R 255.255.255.0 C 255.255.255.0

R = received from the neighbor, C = configured locally. Fix: make both sides match (no ip ospf hello-interval on R2, or set the same values on both).

Fault 2: area mismatch

R4's Gi0/0 is in area 1 (network 10.0.14.0 0.0.0.3 area 1) while R1's Gi0/1 is in area 0. No neighbor forms. R1 logs:

%OSPF-4-ERRRCV: Received invalid packet: mismatched area ID from backbone area must be virtual-link but not found from 10.0.14.2, GigabitEthernet0/1

Fix: put both ends of the link in the same area. show ip ospf interface brief on each side shows the area column.

Fault 3: passive interface on a transit link

passive-interface GigabitEthernet0/0 on R1 by mistake (common after passive-interface default without the matching no passive-interface). R1 has no neighbors on Gi0/0; the 10.0.123.0/24 subnet is still advertised. show ip ospf interface Gi0/0 shows No Hellos (Passive interface); show ip protocols lists Gi0/0 under Passive Interface(s). Fix: no passive-interface GigabitEthernet0/0.

Fault 4: duplicate router ID

R4 was configured with router-id 1.1.1.1 (copy-paste from R1). The neighbors on the shared link cannot form a proper adjacency, and IOS logs messages such as:

%OSPF-4-DUP_RTRID_NBR: OSPF detected duplicate router-id 1.1.1.1 from 10.0.14.2 on interface GigabitEthernet0/1

If the duplicates are not direct neighbors, the symptom is different: both routers keep originating a type 1 LSA with the same Link ID, each overwriting the other, so routes flap and the LSDB churns. Fix: unique router-id on R4, then clear ip ospf process.

Fault 5: MTU mismatch (stuck in ExStart/Exchange)

R4's Gi0/0 has ip mtu 1400, R1's is 1500. Hellos are small and fine, so the neighbors see each other, but DBD packets carry the interface MTU and a router rejects DBDs from a neighbor whose MTU is larger than its own. The adjacency never completes:

R1# show ip ospf neighbor

Neighbor ID     Pri   State           Dead Time   Address         Interface
4.4.4.4           0   EXCHANGE/  -    00:00:37    10.0.14.2       GigabitEthernet0/1
2.2.2.2           1   FULL/BDR        00:00:31    10.0.123.2      GigabitEthernet0/0
3.3.3.3           1   FULL/DR         00:00:35    10.0.123.3      GigabitEthernet0/0

The router with the higher MTU (R1) accepts the neighbor's DBDs and moves on to EXCHANGE; the one with the lower MTU (R4) rejects them and stays in EXSTART, so show ip ospf neighbor on R4 shows 1.1.1.1 in EXSTART. The states may cycle as the neighbor times out and retries. Fix: make the MTUs equal. ip ospf mtu-ignore on the interface disables the check, but Cisco describes it as needed only in rare cases; matching MTU is the correct fix (see Troubleshoot OSPF Neighbors Stuck in Exstart/Exchange State).

Fault 6: subnet mask mismatch on a broadcast network

R3's Gi0/0 is 10.0.123.3 255.255.255.128 while R1 and R2 use /24. On broadcast networks the mask in the hello must match, so R3 forms no neighbors and the debug shows Mask R 255.255.255.128 C 255.255.255.0. Two routers in completely different subnets (a typo like 10.0.132.3) also never become neighbors. Fix the addressing. (On point-to-point network types RFC 2328 says the mask field is not checked, which is one reason the same mistake can behave differently on a point-to-point link.)

Fault 7: network statement wildcard wrong

R3 has network 192.168.3.0 0.0.0.0 area 0. That matches only the address 192.168.3.0, not R3's interface 192.168.3.1, so Gi0/1 is not in OSPF and 192.168.3.0/24 vanishes from every other router's table. Symptoms: Gi0/1 missing from show ip ospf interface brief on R3; the bad statement visible in show ip protocols. Fix: no network 192.168.3.0 0.0.0.0 area 0 then network 192.168.3.0 0.0.0.255 area 0 (or ip ospf 1 area 0 on the interface).

Fault 8: no DR possible (all priorities 0)

If every router on a broadcast segment has ip ospf priority 0, no DR or BDR is elected. Neighbors stay 2WAY/DROTHER with each other forever, no adjacency reaches Full, and no routes are learned over the segment. Fix: give at least one router a non-zero priority (or use point-to-point if there are only two routers).

Fault 9: network type mismatch

One side ip ospf network point-to-point, the other left as broadcast. Timers match, so a neighbor appears (possibly Full), but routes over the link are missing or one-sided. show ip ospf interface shows "Network Type BROADCAST" on one end and "POINT_TO_POINT" on the other. Fix: same network type on both ends.

Tip: Also remember the non-OSPF causes: an inbound ACL that denies OSPF (permit ospf or protocol 89 before any deny), mismatched authentication (configure the same type and key on both ends), and an interface that is simply shut down.

Recap

  • OSPF: link-state, IP protocol 89, hellos to 224.0.0.5, DROTHER updates to 224.0.0.6, AD 110, metric = sum of outgoing interface costs (reference 100 Mbps / bandwidth, min 1).
  • Neighbors must match area, subnet/mask (broadcast), hello/dead (10/40 broadcast and p2p, 30/120 NBMA), authentication and stub flag; RIDs unique; MTU equal to reach Full. Process ID and priority need not match.
  • States: Down, Init, 2-Way, ExStart, Exchange, Loading, Full. DROTHER pairs stay 2-Way (normal); stuck ExStart/Exchange = MTU.
  • Point-to-point: no DR/BDR, neighbor shows FULL/ -; configure ip ospf network point-to-point on both ends.
  • DR/BDR: highest priority (default 1, 0 = never), then highest RID; non-preemptive; BDR takes over when DR fails.
  • RID: router-id command, else highest up loopback, else highest up interface; change takes effect after clear ip ospf process.
  • Network command matches interface IPs with a wildcard; passive-interface stops hellos but still advertises the subnet; default-information originate needs a default route unless always.

3.5 Purpose, functions and concepts of first hop redundancy protocols

The exam topic says "describe purpose, functions and concepts", so expect conceptual questions: what problem FHRPs solve, how the virtual address works, which protocol is Cisco-proprietary, which one load-balances, default priorities, preemption and the virtual MAC formats. Configuration is supporting detail, but HSRP is short to configure and the lab makes the concepts concrete.

The problem: one default gateway

End hosts are configured (statically or by DHCP) with exactly one default gateway IP address. They do not run routing protocols and cannot discover a second router on their own. If a LAN has two routers for redundancy but every host points at R1's address, then when R1 fails every host loses off-subnet connectivity, even though R2 is healthy and connected to the same LAN. Reconfiguring hundreds of hosts is not a recovery plan.

The solution: a virtual router

A first hop redundancy protocol lets two or more routers (or Layer 3 switches) on the same subnet cooperate to present one virtual router:

  • A virtual IP address (VIP) on the subnet. Hosts use the VIP as their default gateway.
  • A virtual MAC address that goes with the VIP. When a host ARPs for the VIP, the router currently forwarding answers with the virtual MAC, not its own burned-in MAC.
  • The routers exchange periodic hello messages (multicast) to elect which one forwards traffic for the VIP and to detect failure.
  • On failure, a standby router takes over the VIP and virtual MAC and sends a gratuitous ARP so the switches update their MAC address tables to the new port. The hosts notice nothing: their ARP cache entry (VIP to virtual MAC) is still correct.

FHRPs protect the first hop only: the gateway from the host's point of view. They do nothing for routing beyond the gateway; that is the routing protocol's job (and object tracking, below, connects the two).

HSRP (Hot Standby Router Protocol)

Cisco-proprietary, the most common FHRP on Cisco networks and the one you are most likely to configure.

  • Roles: one active router forwards traffic sent to the virtual MAC and answers ARP for the VIP. One standby router monitors the active and takes over if it fails. Any other routers in the group are in the listen state.
  • Election: highest priority (0 to 255, default 100); tie broken by the highest interface IP address.
  • Preemption is disabled by default. A router with a higher priority that comes up later does not take the active role unless standby group preempt is configured on it. Without preempt, whoever became active first stays active.
  • Timers: hello every 3 s, hold time 10 s (the standby declares the active dead after 10 s without hellos). Adjustable with standby group timers hello hold.
  • Transport: UDP port 1985.
  • States: Initial, Learn, Listen, Speak, Standby, Active.
  • VIP: must be in the interface's subnet and must be an unused address (not either router's own interface IP).

Both routers in a group must run the same version. Group numbers only need to be unique per interface/VLAN, but a common practice is group number = VLAN number, which is one reason v2's larger range matters.

Load sharing with multiple groups

One HSRP group has one active router, so the standby's uplink sits idle. To use both routers, run a separate group per VLAN and make different routers active: R1 active for VLAN 10 (group 10), R2 active for VLAN 20 (group 20). Each router backs up the other. This is per-subnet load sharing, not per-host (compare GLBP).

Object tracking

HSRP hellos only prove that the active router is alive on the LAN. If R1's WAN uplink fails, R1 still sends hellos and stays active, attracting all traffic it can no longer forward. Tracking fixes this: R1 watches an object (an interface's line protocol, or a route), and when the object goes down R1 lowers its own HSRP priority by a decrement (default 10). If the reduced priority falls below R2's and R2 has preempt configured, R2 takes over.

R1(config)# track 1 interface GigabitEthernet0/1 line-protocol
R1(config-track)# exit
R1(config)# interface GigabitEthernet0/0
R1(config-if)# standby 10 track 1 decrement 20

Exam trap: Tracking only lowers the priority. The other router takes over only if it has preempt configured and its priority is now higher. And the decrement must be large enough: 110 minus the default decrement of 10 is 100, which only ties R2's 100. Do not design around a tie; use a decrement that takes R1 clearly below the other router (20 here gives 90).

VRRP (Virtual Router Redundancy Protocol)

The open standard (IETF). VRRPv2 (RFC 3768) is IPv4 only; VRRPv3 (RFC 5798) supports IPv4 and IPv6. Use it in multivendor networks.

  • Roles: one master (forwards) and one or more backups.
  • Priority: default 100, configurable 1 to 254. The router that actually owns the VIP (the VIP is its real interface address) is the IP address owner, has fixed priority 255 and is always master when it is up.
  • VIP can be a real interface address of one of the routers (unlike HSRP).
  • Preemption is enabled by default.
  • Timers: advertisements every 1 s by default; a backup declares the master down after about three advertisement intervals plus a small skew based on its priority (about 3.6 s at priority 100).
  • Transport: its own IP protocol number 112 (not UDP), multicast 224.0.0.18 (IPv6: FF02::12).
  • Virtual MAC: 0000.5e00.01XX, XX = the VRID (group) in hex (IPv6: 0000.5e00.02XX).
! Classic IOS (VRRPv2)
R1(config-if)# vrrp 10 ip 192.168.10.1
R1(config-if)# vrrp 10 priority 110
! IOS XE with VRRPv3 enabled uses an address-family form instead:
R1(config)# fhrp version vrrp v3
R1(config)# interface GigabitEthernet0/0
R1(config-if)# vrrp 10 address-family ipv4

GLBP (Gateway Load Balancing Protocol)

Cisco-proprietary, and the only one of the three that load-balances within a single group: different hosts on the same subnet, all using the same gateway IP, are spread across several routers.

  • AVG (active virtual gateway): one per group, elected by highest priority (default 100), then highest IP. The AVG answers every ARP request for the VIP, handing out different virtual MAC addresses to different hosts.
  • AVF (active virtual forwarder): up to 4 per group. Each owns one virtual MAC and forwards traffic sent to it. The AVG is usually also an AVF.
  • Virtual MAC: 0007.b400.XXYY, XX = group number, YY = AVF number (group 1: 0007.b400.0101, 0007.b400.0102, ...).
  • Load-balancing method: round-robin by default; also weighted and host-dependent.
  • Preemption: off by default for the AVG role; on by default (with a 30 s delay) for the AVF role.
  • Transport and timers: UDP 3222, multicast 224.0.0.102, hello 3 s, hold 10 s. Groups 0 to 1023.
R1(config-if)# glbp 10 ip 192.168.10.1
R1(config-if)# glbp 10 priority 110
R1(config-if)# glbp 10 preempt
R1(config-if)# glbp 10 load-balancing round-robin

If an AVF fails, another AVF takes over its virtual MAC, so the hosts that were using it keep working. If the AVG fails, the standby AVG takes over the ARP-answering role.
