6.1 How automation impacts network management

Domain 6 is 10 percent of the exam, and most of it is vocabulary and concepts rather than configuration. Cisco tests whether you can recognize the terms it uses (controller, northbound, southbound, underlay, overlay, fabric, idempotent, agentless, CRUD) and pick the right one in a scenario. You already write code, so this lesson spends little time on programming itself and a lot of time on exactly how Cisco frames each idea.

The problem automation solves

A traditional enterprise network is run box by box. An engineer opens an SSH session to each router or switch, types commands in global configuration mode, checks the result with show commands, and repeats on the next device. That works for ten devices. It breaks down at hundreds or thousands, because every manual step is slow, inconsistent and a chance for a typo.

Network automation means using software (scripts, controllers, configuration management tools) to perform configuration, verification and operational tasks that a human would otherwise do by hand at the CLI. The engineer describes what should happen once, and the software applies it to every device the same way.

Benefits Cisco expects you to name

Exam trap: Automation does not remove the need to understand networking. It also amplifies mistakes: a wrong template pushed by automation breaks every device at once. That is why automated changes still go through testing, peer review and change control. If an answer says automation "eliminates the need for network engineers" or "eliminates all errors," it is wrong.

Configuration drift

Configuration drift is the gradual divergence of a device's actual (running) configuration from its intended, approved configuration. It happens through emergency fixes typed at 2 a.m. and never documented, one-off troubleshooting changes that were never removed, inconsistent manual rollouts, and devices replaced from old backups.

Drift matters because a network that does not match its documentation is unpredictable: security controls may be missing on some devices, troubleshooting assumptions are wrong, and compliance audits fail. In a regulated environment like a GxP site, undocumented drift is also a compliance finding by itself.

Automation addresses drift in three ways:

  • Detection: a tool periodically pulls each running configuration and compares it to the intended configuration. Catalyst Center has a compliance feature that flags devices whose running configuration no longer matches what it provisioned. Ansible's check mode (--check --diff) and Terraform's plan do the same thing for the resources they manage.
  • Remediation: rerunning the same automation puts the device back into the intended state. Because good automation is idempotent (see below), rerunning it is safe.
  • Prevention: if every change must go through the automation pipeline, manual changes become rare and visible.

Infrastructure as code (IaC)

Infrastructure as code means defining infrastructure (network devices, servers, cloud resources) in machine-readable text files that are stored in version control, reviewed like software, and applied by a tool. Key ideas:

Source of truth
The files in the repository (often Git) define what the network should look like. The devices are made to match the files, not the other way around.
Version control
Every change is a commit with an author, a timestamp and a message, so you have a full history and can roll back.
Declarative vs imperative (procedural)
A declarative tool is told the desired end state ("VLAN 10 named USERS must exist") and works out the steps. An imperative tool is told the exact steps in order ("enter config mode, type vlan 10, type name USERS"). Terraform is declarative. Ansible playbooks run tasks in order, but most of its modules are written to reach a declared state.
Idempotency
Applying the same configuration once or many times produces the same result. The second run of an idempotent tool finds nothing to change and reports no changes. This is what makes automation safe to rerun for drift remediation.
CI/CD pipeline
Continuous integration and continuous delivery: proposed changes are automatically tested (syntax checks, lab validation) and then deployed. You only need to recognize the term for the CCNA.

What changes for network engineers

  • From CLI typing to defining intent. The engineer spends more time designing templates, policies and data (variables per site) and less time typing commands device by device.
  • New skills: data formats (JSON, YAML, XML), REST APIs, basic Python, Git, and tools such as Ansible and Terraform. Cisco calls this area network programmability.
  • Centralized management: controllers such as Catalyst Center, Meraki dashboard and SD-WAN Manager become the primary interface instead of individual device CLIs (topic 6.2).
  • Zero-touch provisioning: new devices can boot, contact a controller (for example via Plug and Play in Catalyst Center) and receive their configuration without an engineer consoling in.
  • Operations become data-driven: controllers collect telemetry and health data continuously, and analytics or AI/ML tools find problems that a human would miss (topic 6.4).
  • The fundamentals still matter. You cannot write a correct OSPF template without understanding OSPF, and you cannot troubleshoot a failed automation run without reading show output.

Recap

  • Automation replaces device-by-device CLI work with software that applies changes consistently to many devices.
  • Main benefits: consistency, fewer human errors, speed, scale, compliance and drift detection, lower operational cost.
  • Configuration drift is the gap between running and intended configuration; automation detects and remediates it.
  • Infrastructure as code keeps intended configuration in version-controlled files that act as the source of truth.
  • Idempotent tools produce the same end state no matter how many times they run.
  • Automation amplifies mistakes, so testing and change control still apply, and networking fundamentals still matter.

6.2 Traditional networks compared with controller-based networking

Traditional networking

In a traditional network every device is an independent box:

  • Per-device management. Each router and switch has its own configuration, managed through its own CLI (console, SSH, Telnet), and possibly SNMP for monitoring. There is no single place to see or change the whole network.
  • Distributed control plane. Each device runs its own control plane protocols (OSPF, STP, ARP, CDP and so on) and makes its own forwarding decisions based on what it learned from neighbors. No device has a complete, authoritative view; the network "converges" as devices exchange information.
  • Configuration is imperative and local. To change a policy (say, a QoS marking or an ACL) across the network, an engineer translates the intent into commands and applies them to each relevant device by hand.

The distributed model is resilient (there is no single point of failure for control decisions) and well understood, which is why it is still the foundation of most networks. Its weakness is operational: it is slow, error-prone and hard to keep consistent at scale.

Controller-based networking

A controller-based network adds a central software platform, the controller, that has a network-wide view and manages devices through APIs and protocols instead of a human typing on each device.

  • Centralized management and (some) control. The controller holds the inventory, topology and policy for the whole network. Depending on the architecture it may compute forwarding behavior itself (classic OpenFlow SDN) or it may manage and configure devices that still run their own distributed protocols (Catalyst Center with SD-Access, Cisco ACI, SD-WAN Manager).
  • Southbound interface (SBI). The controller talks down to devices using protocols such as NETCONF, RESTCONF, SSH/CLI, SNMP or OpenFlow (topic 6.3).
  • Northbound interface (NBI). The controller exposes REST APIs up to applications, scripts and its own GUI, so humans and programs manage the network through the controller, not the devices.
  • Policy-based / intent-based. The engineer states what they want ("guest users may reach only the Internet," "voice traffic gets priority") and the controller translates that into device configuration.
  • Data plane stays on the devices. Even in a controller-based network, user traffic is forwarded by the switches and routers. The controller is not in the traffic path.

Policy-based and intent-based networking

Intent-based networking (IBN) is Cisco's term for a closed loop in which the network is managed by business intent rather than device commands:

  1. Translation: the administrator expresses intent ("the Finance group must not reach the lab network"); the controller translates it into policy.
  2. Activation: the controller pushes the resulting configuration to all relevant devices automatically.
  3. Assurance: the controller continuously collects telemetry to verify that the network actually behaves as intended, and flags or fixes deviations.

Policy-based networking is the same idea at a smaller scale: you define a policy once (for example, an application QoS policy or a group-based access policy) and the controller renders it into per-device configuration.

6.3 Controller-based, software-defined architecture (overlay, underlay, fabric)

Software-defined networking (SDN) is an architecture that separates the decision-making part of the network (control) from the packet-moving part (data), centralizes control and management in software (a controller), and exposes the network to programs through APIs. To answer SDN questions you need three building blocks: the planes, the controller with its northbound and southbound interfaces, and the fabric terms underlay and overlay.

The three planes

Every network device's work can be split into three logical planes. Cisco asks you to place a given function in the right plane, so learn the examples.

PlaneJobExamples on a Cisco router or switch
Data plane (forwarding plane)Moves user packets and frames from an ingress interface to an egress interface. Works per packet, at high speed, usually in hardware (ASICs and TCAM on switches, CEF on routers).Looking up the destination in the MAC address table or the FIB (CEF) and forwarding; rewriting the Layer 2 header; decrementing TTL; applying ACL permit/deny decisions to traffic; NAT translation of packets; QoS marking and queuing; encapsulating and de-encapsulating (802.1Q tags, VXLAN, GRE, IPsec).
Control planeBuilds the information the data plane uses: routes, neighbor tables, Layer 2 topology. Runs on the device CPU.Routing protocols (OSPF, EIGRP, BGP), building the routing table and FIB; ARP (IPv4) and NDP (IPv6) to build adjacency tables; STP/RSTP to decide forwarding/blocking ports; MAC address learning (Cisco study material usually groups it with the control plane, even though switch hardware performs it); LACP negotiation; CDP/LLDP neighbor discovery.
Management planeLets administrators and systems configure, monitor and manage the device itself.SSH and Telnet CLI sessions; console; SNMP; syslog; the HTTPS GUI; NETCONF and RESTCONF API access; AAA for administrator logins (TACACS+, RADIUS).

Remember: forwarding a packet, ACL filtering of transit traffic, NAT and encapsulation are data plane. OSPF, ARP, STP and building the routing table are control plane. SSH, SNMP, syslog and NETCONF/RESTCONF are management plane. A protocol packet such as an OSPF hello is itself received by the device, but the function it serves is control plane.

6.3.a Separation of control plane and data plane

In a traditional device both planes live in the same box: the CPU runs OSPF and programs the forwarding hardware a few centimeters away. Every device computes its own view of the network, which is the distributed control plane from topic 6.2.

The classic SDN idea (formalized around OpenFlow) is to move the control plane off the devices into a central controller. The controller computes forwarding behavior for the whole network and programs each device's flow tables. The devices become simpler forwarding elements that only run the data plane (and a small agent to talk to the controller).

Why separate them:

  • The controller has a complete network-wide view, so it can make decisions (paths, policies) that consider the whole network rather than one device's neighbors.
  • Policy and forwarding behavior can be changed in one place by software instead of on every box.
  • Forwarding hardware can be simpler and the control software can evolve independently.

Trade-offs: the controller becomes critical infrastructure (it is usually deployed as a cluster for redundancy), and the devices depend on reaching it for changes.

Most Cisco controller-based solutions use a hybrid model rather than pure separation. In SD-Access, switches still run IS-IS and LISP; in SD-WAN, routers still forward and run local protocols while the SD-WAN Controller centralizes overlay routing (OMP) and policy; in ACI, the APIC defines policy while the switches run the fabric protocols. What is centralized in all of them is management, policy and a network-wide view. On the exam, if a question asks what SDN "separates," the answer is the control plane from the data plane; if it asks what the controller centralizes, think control (and management) functions, never the data plane.

Exam trap: the data plane is never moved to the controller. Packets are always forwarded by the network devices. An answer that says "the controller forwards traffic between hosts" or "SDN centralizes the data plane" is wrong.

6.3.b Northbound and southbound APIs

Picture the controller in the middle of a vertical stack: applications above it, network devices below it. The interfaces are named by direction.

Northbound interface (NBI)

  • Between the controller and the applications, scripts, orchestration tools and dashboards above it.
  • Almost always a REST API over HTTPS, exchanging JSON (sometimes XML). Topic 6.5 covers REST in detail.
  • Abstracts the network: an application asks for "all devices," "the health of site Boston," or "apply policy X" without knowing device CLI syntax.
  • Examples: the Catalyst Center Intent API (/dna/intent/api/v1/...), the Meraki Dashboard API, the SD-WAN Manager REST API, the APIC REST API. Cisco's documentation describes the Catalyst Center Intent API as a "Northbound REST API."

Southbound interface (SBI)

  • Between the controller and the network devices below it. Used to push configuration and read state.
  • Protocols you must recognize:
Southbound protocolWhat to know
OpenFlowOpen standard (Open Networking Foundation) that lets a controller program flow tables directly in switches. The textbook example of pure control/data plane separation; used by controllers such as OpenDaylight.
NETCONFIETF protocol for configuring devices using YANG data models, XML encoding, over SSH on TCP port 830. Enabled on IOS XE with netconf-yang.
RESTCONFIETF protocol (RFC 8040) that offers YANG-modeled data through a REST-style HTTPS API, with JSON or XML encoding. Enabled on IOS XE with restconf plus ip http secure-server.

RESTCONF uses REST principles, but when a controller uses it to configure a router it is acting as a southbound protocol. If a question asks which API "a Python application uses to get the device list from Catalyst Center," the answer is northbound (REST).

Underlay, overlay and fabric

Modern controller-based designs build virtual networks on top of a physical network. Three terms describe this:

Underlay
The physical network: the switches, routers, links and the routing protocol that gives every device IP reachability to every other device. Its only job is to carry packets between network devices' loopback addresses reliably and quickly. End-user subnets are not in the underlay.
Overlay
Virtual (logical) networks built on top of the underlay using tunnels. Traffic between endpoints is encapsulated at the ingress device, carried across the underlay as ordinary IP packets, and de-encapsulated at the egress device. The overlay defines the user-facing networks and policy, independent of the physical layout.
Fabric
The combination of underlay and overlay operating as one system, usually managed by a controller. To endpoints and administrators it behaves like one large switch. Cisco uses "fabric" for SD-Access (campus), ACI (data center) and SD-WAN (WAN).

Analogy: the underlay is the road system; the overlay is the set of delivery routes, each in sealed trucks, that run over those roads without the roads needing to know what is inside.

Cisco SD-Access

SD-Access is Cisco's campus fabric, managed by Catalyst Center with Cisco ISE providing identity and policy. Learn its terms at a recognition level:

Recap

  • Data plane forwards packets (MAC/FIB lookup, ACL, NAT, encapsulation); control plane builds the tables (OSPF, ARP, STP); management plane is for admins (SSH, SNMP, syslog, NETCONF/RESTCONF).
  • SDN separates the control plane from the data plane and centralizes control in a controller; the data plane stays on the devices.
  • Northbound API = controller to applications, typically REST with JSON. Southbound = controller to devices: OpenFlow, NETCONF (SSH 830, XML), RESTCONF (HTTPS, JSON/XML), OpFlex, SSH/CLI, SNMP.
  • Underlay = physical routed network; overlay = tunneled virtual networks; fabric = both working together under a controller.
  • SD-Access: IS-IS underlay (LAN Automation), VXLAN data plane, LISP control plane, TrustSec SGT policy plane; edge, border and control-plane nodes.
  • SD-WAN: Manager (vManage), Controller (vSmart, OMP), Validator (vBond), WAN edges forwarding over IPsec.

6.4 AI (generative and predictive) and machine learning in network operations

This topic was added in blueprint v1.1. Cisco tests concepts here, not product configuration: what the terms mean, which kind of AI fits which operational job, and what the risks are. Keep your answers general; the exam does not expect detailed knowledge of any one product's algorithms.

The vocabulary

Artificial intelligence (AI)
The broad field of building systems that perform tasks that normally need human intelligence: recognizing patterns, making predictions, understanding language, making decisions.
Machine learning (ML)
A subset of AI in which a system learns patterns from data instead of being explicitly programmed with rules. You give it examples (data), it builds a model, and the model makes predictions or decisions on new data.
Deep learning (DL)
A subset of ML that uses multi-layer neural networks. It powers image and speech recognition and the large language models (LLMs) behind generative AI.
Model
The output of training: the learned function that maps inputs to predictions.
Training vs inference
Training is learning the model from data; inference is using the trained model on new data.

The nesting is the classic exam point: deep learning is a subset of machine learning, which is a subset of AI.

Predictive AI in network operations

Predictive AI analyzes historical and real-time data to detect patterns, spot deviations and forecast what will happen. It produces scores, alerts, forecasts and likely causes, not new content. This is the AI that network monitoring and assurance platforms have used for years. Typical uses:

  • Baselining: learning what "normal" looks like for each network, site, device or time of day, instead of using one fixed threshold for everyone. A 300 ms DHCP response may be normal at one site and a problem at another.
  • Anomaly detection: flagging behavior that deviates from the learned baseline, such as a sudden rise in authentication failures, an unusual traffic volume, or a client onboarding time far outside the norm.
  • Forecasting and capacity planning: predicting when a link or a WAN circuit will reach saturation, or when wireless density will exceed capacity.
  • Failure prediction: identifying patterns (rising error counters, temperature, memory leaks) that tend to come before failures, so you can act before an outage.
  • Root cause analysis and event correlation: grouping hundreds of related alarms into one incident and pointing at the most likely cause, which cuts alert noise.
  • Security analytics: spotting compromised hosts or unusual flows by behavior rather than signatures.

Examples in the Cisco portfolio, described only at the level Cisco's own documentation does:

  • Catalyst Center Assurance and AI Network Analytics: Cisco's data sheet lists AI-driven personalized baselining, AI-driven anomaly detection and AI-enhanced Radio Resource Management (RRM) among Catalyst Center's features. Assurance uses the data it collects to detect issues, compare against baselines, and suggest root causes and fixes.
  • Cisco ThousandEyes: monitors performance and availability from users to applications across networks you own and networks you do not own (ISPs, the Internet, cloud and SaaS providers) using agents and synthetic tests, and applies analytics to that data. Catalyst Center can deploy ThousandEyes agents on supported switches.

Generative AI in network operations

Generative AI creates new content (text, code, configuration, summaries) in response to a prompt. It is built on large language models trained on huge amounts of text. In network operations it shows up as:

  • Natural-language assistants: asking questions in plain English ("Which access points at the Cambridge site had the most client failures yesterday?") instead of navigating menus or writing queries. Cisco offers an AI Assistant across products such as Catalyst Center and ThousandEyes.
  • Configuration and script generation: drafting an ACL, a VLAN configuration, an Ansible playbook or a Python script from a description.
  • Summarization and explanation: summarizing long logs or incident timelines, explaining what a show output or an error means, translating a configuration from one platform's syntax to another.
  • Documentation: writing change requests, runbooks, design documents and post-incident reports from raw notes.

Risks and required controls for generative AI

  • Hallucination: the model can produce confident, plausible output that is wrong: a command that does not exist on this platform, the wrong syntax, a wrong default, or an invented explanation.
  • Human validation is mandatory: treat generated configuration like a junior engineer's draft. Review it, test it in a lab, and push it through normal change control.
  • Data privacy and confidentiality: pasting running configurations, logs or diagrams into a public AI service can leak passwords, keys, IP plans and customer data. Use approved tools, remove secrets, and follow company policy.
  • Stale or generic knowledge: a model may not know your environment, your standards or the latest software version.
  • Security of the AI itself: prompt injection and over-trusting an assistant that can make changes; keep humans in the approval loop for anything that changes the network.

AIOps

AIOps (AI for IT operations) is the use of AI and ML on operational data (metrics, events, logs, traces, tickets) to automate and improve operations: correlating events, reducing alert noise, detecting anomalies, finding root causes and, in mature setups, triggering automated remediation (for example, running an Ansible playbook when a known issue is detected). It combines topic 6.4 with the automation tools in topics 6.1 and 6.6: analytics decide what is wrong, automation does something about it, and humans approve and supervise.

Exam trap: do not mix the two kinds of AI. "Detects that a site's latency is abnormal compared with its baseline" is predictive. "Writes a VLAN configuration from a plain-English request" is generative. Also, ML needs data: a question asking what a model requires before it can find anomalies is looking for "a baseline built from historical data."

Recap

  • AI contains ML, which contains deep learning; LLMs behind generative AI are deep learning models.
  • Supervised learning uses labeled data; unsupervised finds patterns in unlabeled data; reinforcement learns from rewards.
  • Predictive AI: baselining, anomaly detection, forecasting, failure prediction, root cause (for example Catalyst Center Assurance, ThousandEyes).
  • Generative AI: natural-language assistants, config and script drafts, summaries, documentation.
  • Generative AI risks: hallucination, data privacy, overtrust; always validate and test before deploying.
  • AIOps applies AI/ML to operations data to correlate, detect and remediate.

6.5 REST-based APIs (authentication types, CRUD, HTTP verbs, data encoding)

An API (application programming interface) is a defined way for one program to ask another program to do something or return data. REST (Representational State Transfer) is an architectural style for APIs, defined by Roy Fielding in his 2000 dissertation. REST is not a protocol, but in practice REST APIs use HTTP/HTTPS as their transport, identify things with URIs, and exchange data as JSON or XML. Catalyst Center, Meraki, SD-WAN Manager, APIC and IOS XE (through RESTCONF) all expose REST APIs.

REST constraints

An API is "RESTful" when it follows these architectural constraints. Cisco's materials list them, so learn the names:

ConstraintMeaning
Client-serverThe client (script, app) and the server (controller, device) are separate. The client handles the user side; the server stores data and does the work. Either can change independently as long as the interface stays the same.
StatelessEvery request carries everything the server needs to process it. The server keeps no client session state between requests. This is why a token or credentials travel in every request.
CacheableResponses must say whether they can be cached. Cacheable responses can be reused by the client or an intermediary, reducing load.
Uniform interfaceResources are identified by URIs and manipulated through representations (such as JSON) using a standard set of methods; messages are self-descriptive (headers say what format the body is in); responses can include links to related resources (hypermedia).
Layered systemThe client cannot tell whether it is talking to the end server or to an intermediary such as a load balancer, proxy or API gateway.
Code on demand (optional)The server may send executable code (such as JavaScript) to the client. This is the only optional constraint.

Remember: six REST constraints: client-server, stateless, cacheable, uniform interface, layered system, code on demand (optional). "Stateless" is the most tested one.

Scheme
The protocol: https (TCP 443 by default) or http (TCP 80). Production APIs use HTTPS.
Host (authority)
The server's DNS name or IP address, optionally followed by :port.
Resource path
Identifies the resource or collection: here /dna/intent/api/v1/network-device, the device inventory. Paths often contain a version (v1) and can identify one item, such as /network-device/{id}.

Start after ?, are key=value pairs separated by &, and filter, sort or page the results. Spaces and special characters are percent-encoded (%20 is a space).

CRUD and HTTP verbs

CRUD stands for Create, Read, Update, Delete, the four basic operations on data. REST maps them to HTTP methods (verbs):

Safe means the method does not change server state (read-only). Idempotent means sending the same request once or ten times leaves the server in the same state. Two POSTs to create a VLAN can create two objects or return an error; two identical PUTs leave one resource with the same content.

PUT vs PATCH

Suppose the resource for interface Gi1/0/5 is {"description": "Printer", "enabled": true, "mtu": 1500}.

  • PATCH with {"description": "Lab printer"} changes only the description. enabled and mtu keep their values.
  • PUT with {"description": "Lab printer"} replaces the whole resource with what you sent, so fields you left out may be removed or reset to defaults. With PUT you send the complete representation.

PUT, POST, GET and DELETE are defined in RFC 9110 (HTTP Semantics); PATCH is defined separately in RFC 5789, which states that PATCH is "neither safe nor idempotent" in general. RESTCONF on IOS XE follows the same pattern: GET reads, POST creates, PUT creates or replaces, PATCH updates (merges), DELETE deletes.

Exam trap: "Update" maps to two verbs: PUT (replace) and PATCH (partial). "Create" is POST. GET never carries a body and never changes data. If a question asks which method retrieves the device list, the answer is GET, not POST, even though POST is what you use to get a Catalyst Center token.

Authentication types

Basic authentication
The client sends Authorization: Basic followed by base64 of username:password. Base64 is encoding, not encryption: anyone who captures it can decode it. Use only over HTTPS. Example: admin:cisco123 becomes YWRtaW46Y2lzY28xMjM=.
Bearer / token authentication
The client first authenticates once (often with Basic) and receives a token, then sends the token in each request, typically Authorization: Bearer <token>. Tokens expire, can be revoked, and keep the password off the wire for most requests.
API key
A long secret string issued to a user or application, sent in a header (or less safely a query parameter) on every request. Simple, but a leaked key works until it is revoked. The Meraki Dashboard API uses an API key generated in the dashboard.
OAuth 2.0
An authorization framework in which an authorization server issues limited, scoped access tokens to a client application, often on behalf of a user who approves access, without giving the application the user's password. The client then presents the access token (as a bearer token) to the API. Common for cloud and SaaS APIs.

Catalyst Center: token via POST, then X-Auth-Token

Cisco's Catalyst Center API documentation describes this two-step flow:

  1. Send POST to /dna/system/api/v1/auth/token with HTTP Basic authentication (username and password).
  2. The response body is JSON with a Token field.
  3. Send that token in the X-Auth-Token header of every subsequent request.
  4. The token lifetime is 60 minutes; after that, calls return 401 and you request a new token.

Data encoding: JSON, XML, YAML

REST bodies need a structured, machine-readable format. Three appear on the exam:

  • JSON (JavaScript Object Notation): the default for most REST APIs, including Catalyst Center and Meraki. Media type application/json. Covered in depth in topic 6.7.
  • XML (Extensible Markup Language): tag-based, used by NETCONF and supported by RESTCONF. Media type application/xml.
  • YAML (YAML Ain't Markup Language): indentation-based and very readable; used mainly for Ansible playbooks and inventories rather than as an API body format.

6.6 Configuration management mechanisms such as Ansible and Terraform

The exam verb here is "recognize the capabilities." You will not write playbooks on the exam, but you must know what each tool is, how it connects to devices, what language its files use, and whether it is agent-based or agentless, push or pull, declarative or procedural.

The concepts that distinguish the tools

Agent-based vs agentless
An agent-based tool needs its own software (an agent) installed and running on every managed node. An agentless tool uses access methods the node already has: SSH, NETCONF, or a REST API. Most network devices cannot run third-party agents, which is a big reason Ansible became the default network automation tool.
Push vs pull
In a push model the central server connects out to the nodes and pushes changes when an administrator runs the job. In a pull model the agent on each node periodically contacts the server, pulls its desired configuration and applies it.
Declarative vs procedural (imperative)
Declarative: describe the end state and let the tool figure out the steps (Terraform, Puppet). Procedural: describe the ordered steps (Ansible playbooks run tasks in order, although each module aims for a declared state).
Idempotency
Running the same automation repeatedly produces the same end state; when nothing needs changing, nothing is changed and the tool reports no changes.
Configuration management vs provisioning
Configuration management maintains the settings of devices and servers that already exist (Ansible, Puppet, Chef). Provisioning creates the infrastructure itself: VMs, cloud networks, controller objects (Terraform's main strength). The tools overlap, and teams often use Terraform to build and Ansible to configure.

Ansible

Ansible is an open-source automation tool, sponsored by Red Hat and written in Python.

  • Agentless: nothing is installed on managed nodes. For network devices it connects with SSH (the network_cli connection), NETCONF, or the device's HTTP/REST API.
  • Push model: the administrator runs a playbook on the control node, which connects out to the managed nodes and pushes the changes.
  • Control node: the machine where Ansible is installed and run (Linux, macOS, or Windows only through WSL). Requires Python. Managed Linux hosts need Python; network devices do not.
  • Inventory: the list of managed nodes and groups, in INI or YAML format, with per-host or per-group variables (address, platform, credentials).
  • Playbook: a YAML file containing one or more plays. A play maps a group of hosts to an ordered list of tasks. Each task calls one module.
  • Modules: the units of work. Network modules are delivered in collections and named by fully qualified collection name, for example cisco.ios.ios_config (push configuration lines), cisco.ios.ios_command (run show/exec commands; it cannot enter configuration mode), cisco.ios.ios_facts, and resource modules such as cisco.ios.ios_vlans and cisco.ios.ios_interfaces.
  • Templates and variables: Jinja2 templates plus per-device variables generate device-specific configurations from one template.
  • Idempotent: ios_config compares the lines you want against the running configuration and only sends what is missing; the second run reports changed=0. The module's documentation (Ansible's cisco.ios collection) warns that abbreviated commands (such as int g1) are not idempotent, because lines must match the running configuration exactly.
  • Check mode: ansible-playbook --check --diff reports what would change without changing it, which is a drift report.
  • Secrets: Ansible Vault encrypts passwords stored in variable files.

Terraform

Terraform is HashiCorp's infrastructure-as-code tool.

  • Declarative: configuration files describe the desired end state. HashiCorp's own tutorial says the language "describes the desired end-state for your infrastructure."
  • HCL: files are written in the HashiCorp Configuration Language (.tf files), a human-readable language built from blocks such as terraform, provider, resource, variable and output.
  • Providers: plugins that let Terraform talk to a platform's API: AWS, Azure, Google Cloud, VMware, and Cisco platforms such as Catalyst Center, ACI and Meraki (Cisco's Catalyst Center developer page lists Terraform providers). Providers are downloaded from the Terraform Registry by terraform init.
  • Agentless: Terraform runs on your workstation or a CI server and calls APIs; nothing is installed on the managed infrastructure.
  • State file: Terraform records what it manages in a state file, terraform.tfstate by default (JSON), which maps the resources in your configuration to real-world objects. Each plan compares configuration, state and reality. Teams store state remotely (with locking) so everyone works from the same truth. State can contain secrets, so protect it.
  • Workflow: write configuration, then terraform init (download providers), terraform plan (preview: + create, ~ update in place, - destroy, -/+ replace), terraform apply (make the changes after confirmation), and terraform destroy (remove everything it manages).
  • Typical role: provisioning and lifecycle of infrastructure (cloud VPCs, VMs, controller objects), more than line-by-line device configuration.

Puppet and Chef (context)

These older configuration management tools came from server administration. Know their model so you can contrast them with Ansible:

  • Puppet: agent-based, pull model. The Puppet agent on each node sends facts to the Puppet primary server (formerly called the master), requests a compiled catalog, and enforces it. 6.7 Components of JSON-encoded data

JSON (JavaScript Object Notation) is the data format of almost every REST API you will meet, and it is defined by RFC 8259. Exam questions show a JSON exhibit and ask you to identify a value's type, count objects, arrays or key/value pairs, find a value, or spot why a snippet is invalid. These are easy points if you know the rules exactly.

The building blocks

A JSON text is a single value. There are six value types: two structured types and four primitive types (counting true/false as one boolean type).

TypeSyntaxExampleNotes
Object{ }{"vlan": 10, "name": "USERS"}An unordered collection of zero or more key/value pairs (RFC 8259 calls them name/value pairs or members). Keys are strings. Pairs are separated by commas; key and value are separated by a colon.
Array[ ][10, 20, 30]An ordered list of zero or more values, separated by commas. Values can be of mixed types, including objects and arrays.
String" ""GigabitEthernet1/0/1"Unicode text in double quotes only. Special characters are escaped with a backslash: \", \\, \n, \t, and \u00e9 for the character é.
Numberdigits1500, -3, 0.75, 1e3No quotes. Integer or decimal, optional minus sign and exponent. No leading zeros (007 is invalid), no leading or trailing dot (.5 and 5. are invalid), no hex, no NaN or Infinity.
Booleanliteraltrue, falseLowercase, no quotes. True and "true" are not booleans (the first is invalid, the second is a string).
NullliteralnullLowercase, no quotes. Means "no value."

Remember: curly braces {} = object (key/value pairs). Square brackets [] = array (ordered list of values). Keys are always double-quoted strings. The value type is decided by syntax, not meaning: "10.1.1.1" and "1500" are strings; 1500 is a number.

Syntax rules (what makes JSON valid)

  1. Keys must be strings in double quotes. {hostname: "R1"} and {'hostname': 'R1'} are invalid.
  2. Strings use double quotes only. Single quotes are not JSON.
  3. A colon separates each key from its value; a comma separates pairs in an object and values in an array.
  4. No trailing comma after the last pair or element: [1, 2, 3,] is invalid.
  5. No comments. JSON has no comment syntax (// and # are invalid).
  6. true, false, null are lowercase literals.
  7. Every { needs a matching } and every [ a matching ], correctly nested.
  8. Whitespace (spaces, tabs, newlines) between tokens is insignificant; indentation is only for humans. Unlike YAML, indentation never changes meaning.
  9. Keys within one object should be unique (duplicates make behavior unpredictable).
  10. The top level can be any value, usually an object or an array. Media type: application/json.

Nesting

Objects and arrays can contain each other to any depth. This is how JSON represents structured network data: a device has a list of interfaces, each interface has a list of addresses, each address has an IP and a mask.

Here is the kind of response a RESTCONF GET to /restconf/data/ietf-interfaces:interfaces returns from an IOS XE router (using the standard IETF YANG model, trimmed to two interfaces), with Accept: application/yang-data+json:

{
  "ietf-interfaces:interfaces": {
    "interface": [
      {
        "name": "GigabitEthernet1",
        "description": "Uplink to ISP",
        "type": "iana-if-type:ethernetCsmacd",
        "enabled": true,
        "ietf-ip:ipv4": {
          "address": [
            {
              "ip": "203.0.113.2",
              "netmask": "255.255.255.252"
            }
          ]
        }
      },
      {
        "name": "Loopback0",
        "description": "Router ID",
        "type": "iana-if-type:softwareLoopback",
        "enabled": true,
        "ietf-ip:ipv4": {

              "netmask": "255.255.255.255"
            }
          ]
        }
      }

}

Reading it from the outside in:

  • The whole text is an object with one key, "ietf-interfaces:interfaces" (the colon inside the quotes is part of the key: module name, colon, container name).
  • Its value is an object with one key, "interface", whose value is an array of two objects, one per interface.
  • Each interface object has five keys: name (string), description (string), type (string), enabled (boolean true), and ietf-ip:ipv4 (object).
  • ietf-ip:ipv4 holds address, an array (an interface can have several addresses) containing one object with ip and netmask, both strings.

To reach Loopback0's IP address you follow the path: key ietf-interfaces:interfaces → key interface → array index 1 (second element; indexes start at 0) → key ietf-ip:ipv4 → key address → index 0 → key ip = "10.255.0.1". In Python that is data["ietf-interfaces:interfaces"]["interface"][1]["ietf-ip:ipv4"]["address"][0]["ip"].

How to count objects, arrays and key/value pairs

Exhibit questions often ask "how many objects / arrays / key-value pairs are shown?" Use a mechanical method:

  • Objects: count the opening curly braces { (outside of strings). Include the outermost one.
  • Arrays: count the opening square brackets [.
  • Key/value pairs: count the keys, that is, the quoted strings followed by a colon, at every level. A key whose value is an object or array still counts as one pair; the pairs inside it count separately.
  • Elements of an array: count the comma-separated values at that array's top level only.

Applying this to the interface exhibit above:

Tip: when counting quickly on the exam, scan once for {, once for [, and once for ": (a closing quote followed by a colon marks a key). Be careful with values that contain colons, such as "iana-if-type:ethernetCsmacd" or a time like "10:42:07"; those colons are inside a string and are not key separators.

Recap

  • Six JSON value types: object {}, array [], string (double quotes), number, boolean (true/false), null.
  • Objects hold key/value pairs; keys are double-quoted strings; arrays are ordered lists of values.
  • Invalid JSON: single quotes, unquoted keys, trailing commas, comments, capitalized True/Null, leading zeros, mismatched brackets.
  • Count objects by {, arrays by [, key/value pairs by keys at every level.
  • Anything in quotes is a string, even "10" or "true".
  • JSON: REST APIs; XML: NETCONF (and RESTCONF option); YAML: Ansible, indentation-sensitive.
