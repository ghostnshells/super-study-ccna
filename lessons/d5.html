5.1 Key security concepts (threats, vulnerabilities, exploits, mitigation)

You already work in security, so this topic is mostly about matching your vocabulary to Cisco's. The exam asks you to define four terms, recognize named attacks from a short description, and pick the Cisco feature that mitigates each one. The second half of the domain (5.3, 5.6, 5.7) is where you configure those mitigations.

The four core terms as Cisco uses them

Vulnerability
A weakness that could compromise security: a software bug, a weak default password, an open management port, an unlocked wiring closet.
Exploit
The thing that takes advantage of a specific vulnerability: a piece of code, a tool, or a technique. An exploit is useless against a system that does not have the matching vulnerability.
Threat
The potential for a vulnerability to be exploited, usually by a threat actor (person, group, or automated malware). A threat exists when someone has the capability and intent and a vulnerability is present.
Mitigation technique
Any control that reduces or removes the chance that a vulnerability is exploited or limits the damage: patching, ACLs, port security, training, MFA.

Two related words show up in answer choices. Attack vector is the path an attacker uses to get in (email, an exposed VTY line, a switch port in a lobby). Risk combines the likelihood of a threat exploiting a vulnerability with the impact if it does.

Exam trap: "A weakness in a system" is a vulnerability, not a threat. "Code written to take advantage of a weakness" is an exploit. "The potential for harm" is a threat. Read the noun the question is defining, not the scenario around it.

Attack types the CCNA names

Denial of service (DoS) and distributed DoS (DDoS)

A DoS attack exhausts a resource (bandwidth, CPU, memory, a session table) so legitimate users cannot be served. The classic exam example is the TCP SYN flood: the attacker sends many SYNs, often from spoofed sources, and never completes the handshake, filling the target's half-open connection table. A DDoS uses many sources at once, typically a botnet of compromised hosts directed by a command-and-control server.

Spoofing

Spoofing means faking an identity field to impersonate something else.

  • IP address spoofing: forging the source IP. Used to hide the attacker, to bypass source-based ACLs, and as the basis for reflection attacks.
  • MAC address spoofing: forging the source MAC to impersonate a trusted host or to bypass MAC-based filtering.
  • DHCP spoofing: a rogue DHCP server answers clients first and hands out its own address as the default gateway or DNS server, which sets up a man-in-the-middle.
  • DHCP starvation: the attacker sends a flood of DISCOVERs with random client MAC addresses until the real server's pool is empty, often as a first step before running a rogue server.

Reflection and amplification

In a reflection attack the attacker sends requests with the victim's IP as the spoofed source, so a third-party server (the reflector) sends its replies to the victim. It becomes amplification when the reply is much larger than the request, so a small amount of attacker bandwidth becomes a large flood. Open DNS resolvers and NTP servers answering monlist queries are the standard examples. Both rely on UDP, because there is no handshake to prove the source address.

Man-in-the-middle (MITM)

The attacker places itself in the traffic path so it can read or change data. On a LAN the CCNA example is ARP poisoning (ARP spoofing): the attacker sends gratuitous ARP replies claiming the default gateway's IP maps to the attacker's MAC. Hosts update their ARP caches and send off-subnet traffic to the attacker, which forwards it on to the real gateway after reading it. A rogue DHCP server that names itself as the gateway achieves the same result.

Reconnaissance

Information gathering before an attack: public lookups (whois, DNS queries), ping sweeps, port scans, and banner grabbing. Reconnaissance is not damaging by itself, but it tells the attacker what is worth exploiting.

Buffer overflow

The attacker sends more data than a program's buffer can hold, overwriting adjacent memory. Results range from a crash (a DoS) to running the attacker's code. The mitigation is patching and secure coding, which on network devices means keeping IOS current and disabling services you do not use.

5.2 Security program elements (user awareness, training, physical access control)

A security program is the organization-wide set of policies and practices around the technology. The CCNA names three elements. Questions are short and usually turn on the difference between awareness and training, or on which physical control stops which attack.

User awareness

Ongoing, informal efforts that keep security in everyone's mind: posters, newsletter reminders, banners, and especially simulated phishing campaigns, where the security team sends harmless fake phishing emails and tracks who clicks. Awareness reaches all users and tells them that threats exist and what to watch for.

User training

Formal, structured instruction: scheduled classes or required online courses, often with a test, covering specific policies and procedures (how to report a suspected phish, how to handle sensitive data, acceptable use). Training is usually tracked for compliance and repeated on a schedule.

Exam trap: Phishing simulation emails and reminder messages are awareness. A formal course that users must attend or complete is training. Both are part of a security program; neither is a technical control.

Physical access control

Physical access defeats most technical controls: anyone at a console port can run password recovery, and anyone in a wiring closet can plug in a rogue device. Cisco expects you to know these controls:

ControlWhat it does
Locks (key, combination, electronic)Keep equipment rooms, racks and wiring closets (IDFs) closed to unauthorized people.
Badge (card) readersGrant entry per person and log who entered and when. Badges can be revoked centrally.
Access control vestibule (mantrap)A small room with two doors where only one can be open at a time, so each person must authenticate before the inner door opens. Defeats tailgating.
Biometric readersFingerprint, palm, iris or face scanners for high-security rooms.
Security cameras (CCTV)Deter and record; detective rather than preventive.
Guards and visitor logsHuman verification and escorting.

Tip: If a question describes someone following an employee through a door, the best physical answer is an access control vestibule (mantrap); the best program answer is awareness and training about tailgating.

Recap

  • Three program elements: user awareness, user training, physical access control.
  • Awareness is ongoing and informal (phishing simulations, reminders); training is formal and structured (courses, tests).
  • An access control vestibule (mantrap) stops tailgating; badge readers add per-person logging.
  • Physical access to a device's console allows password recovery, so locking closets and racks is a security control.

5.3 Configure and verify device access control using local passwords

This is a configuration topic, and the exam tests it in two ways: you configure from a requirement, and you read a show running-config and predict what a user will experience (password prompt or not, user mode or privileged mode, readable password or not). Know where each command lives (line mode or global) and how the commands interact.

Line passwords: password + login

R1(config)# line console 0
R1(config-line)# password C0ns0le!Pass
R1(config-line)# login
R1(config-line)# exec-timeout 5 0
R1(config-line)# exit
R1(config)# line vty 0 4
R1(config-line)# password Vty!Pass2026
R1(config-line)# login
R1(config-line)# transport input ssh telnet
  • password sets the shared line password. login tells the line to prompt for it. You need both.
  • Console with password but no login: no prompt; anyone at the console gets user EXEC. A factory-default console behaves the same way, because it has neither a password nor login.
  • VTY with login but no password: the router rejects remote logins with "Password required, but none set" and closes the session. VTY lines default to login, so a fresh router cannot be telnetted to until you set a password or login local.
  • VTY with no login: anyone who can reach an IP on the device gets in with no password. Never do this.

login local: per-user accounts

R1(config)# username admin privilege 15 algorithm-type scrypt secret Adm1n!2026xyz
R1(config)# username noc algorithm-type scrypt secret N0cRead0nly!
R1(config)# line vty 0 4
R1(config-line)# login local
R1(config-line)# exit
R1(config)# line console 0
R1(config-line)# login local
  • login local makes the line prompt for a username and password checked against the local username database. Any password configured on that line is ignored while login local is set.
  • Per-user accounts give accountability (logs show who logged in) and let you remove one person without changing a shared password.
  • SSH needs a username, so SSH on the VTY lines requires login local (or AAA). Line password with plain login works for Telnet only. SSH itself is covered in topic 4.8.
  • If login local is set and no usernames exist, nobody can log in on that line (on the console this can lock you out until password recovery).

Privilege levels

IOS has levels 0 to 15. Level 1 is user EXEC (R1>), level 15 is privileged EXEC (R1#). Levels 2 to 14 are unused until you move commands into them. A user defined with privilege 15 who logs in through a line using login local lands directly at R1# without typing enable. A user with no privilege keyword is level 1 and must use enable plus the enable secret.

R1# show privilege
Current privilege level is 15

Protecting privileged mode: enable password vs enable secret

R1(config)# enable secret En@ble!Secret26
! or choose the algorithm explicitly:
R1(config)# enable algorithm-type scrypt secret En@ble!Secret26
  • enable password stores the password in clear text (or type 7 if service password-encryption is on). Legacy; avoid it.
  • enable secret stores a one-way hash. If both are configured, the enable secret is used and the enable password is ignored. IOS warns you if you set them to the same value.
  • Telnet/SSH users cannot reach privileged mode at all if no enable password or secret exists (they get "% No password set"), unless their username has privilege 15. The console allows enable with no password when none is set.

Remember: enable secret beats enable password whenever both exist. Line passwords need login to take effect. login local ignores the line password and uses the username database.

The algorithm-type keyword works for both commands:

R1(config)# username backup algorithm-type sha256 secret B@ckup!2026pw

Older IOS releases default enable secret and username ... secret to type 5 (MD5). Newer IOS XE defaults enable secret to type 9. Either way, you can also paste an existing hash by giving the type number first, for example enable secret 9 $9$..., which is how configs are restored from backups.

service password-encryption

R1(config)# service password-encryption
  • Converts every clear-text password in the configuration (line passwords, enable password, username ... password) to type 7, now and when new ones are entered.
  • It does not touch secrets, which are already hashed.
  • Type 7 only prevents shoulder-surfing of a printed config. It is reversible, so treat a type 7 string as clear text.
  • no service password-encryption does not decrypt passwords already stored as type 7; it only stops encrypting new ones.

Exam trap: username bob password X plus service password-encryption gives a reversible type 7 password. username bob secret X gives a hash (type 5, 8 or 9). If a question asks for the most secure local user, pick secret, ideally with algorithm-type scrypt.

Other hardening commands in scope

exec-timeout

Logs out an idle session. Syntax is exec-timeout minutes [seconds] in line mode. The default is 10 minutes. exec-timeout 0 0 disables the timer (common in labs, a finding in an audit).

login block-for (online brute-force protection)

R1(config)# login block-for 120 attempts 3 within 60
R1(config)# login quiet-mode access-class 5
R1(config)# login on-failure log
R1(config)# login on-success log
  • Read it as: if there are 3 failed logins within 60 seconds, block all logins for 120 seconds. The 120-second block is called quiet mode.
  • During quiet mode the device refuses Telnet, SSH and HTTP logins from everyone, except hosts permitted by the optional login quiet-mode access-class ACL (use it so your admin subnet is never locked out). The console is not blocked.
  • Once login block-for is on, a default delay of 1 second applies between login attempts (login delay changes it).
  • Configure login block-for before the related login quiet-mode and login delay commands.

A banner does not enforce anything, but a warning banner supports legal action against intruders. The # is the delimiter you choose.

5.4 Password policy elements (management, complexity, alternatives: MFA, certificates, biometrics)

This is a "describe" topic. You will not configure anything; you need to recognize policy elements and the three alternatives Cisco names. Watch for the gap between the traditional policy many exam items still assume and current NIST guidance; where they differ, answer the question as written.

Password management

  • Lifetime and rotation: traditional policies force a change every 60 to 90 days. NIST SP 800-63B now says verifiers should not require periodic changes, and should force a change only when there is evidence of compromise, because forced rotation produces predictable patterns (Spring2026!, Summer2026!).
  • History (no reuse): prevent reusing the last N passwords, and never reuse the same password across systems.
  • Password managers: store long unique passwords so users do not have to remember them. NIST says verifiers should allow paste and autofill so managers work.
  • Account lockout or throttling: lock or slow down an account after repeated failures to stop online guessing. On IOS this is login block-for (5.3) or the AAA aaa local authentication attempts max-fail command. Lockout can be abused to lock out legitimate users, so throttling is often preferred.
  • Default passwords: change them before a device goes into production.

Complexity and length

ElementTraditional policyCurrent NIST SP 800-63B
Minimum length8 characters15 when the password is the only factor; 8 when it is part of MFA
Maximum lengthOften cappedAllow at least 64 characters
CompositionRequire upper, lower, digit, symbolDo not impose composition rules

The common thread is that length is the strongest factor: each added character multiplies the brute-force search space, and long passphrases are easier to remember than short complex strings.

Alternatives to (or additions to) passwords

Multifactor authentication (MFA)

MFA requires factors from at least two different categories:

FactorExamples
Something you know (knowledge)Password, PIN, security question
Something you have (possession)Phone with an authenticator app or push approval, hardware token, smart card
Something you are (inherence)Fingerprint, face, iris, voice

Exam trap: A password plus a PIN is two factors of the same category, so it is not MFA. A password plus a one-time code from an app on your phone is MFA (know + have).

Digital certificates

A digital certificate binds an identity (a user, a device, a server name) to a public key, and is signed by a certificate authority (CA). The set of CAs, policies and processes that issue and revoke certificates is a public key infrastructure (PKI). The certificate format is X.509. To authenticate, the holder proves it has the matching private key; the verifier checks the CA's signature, validity dates, and revocation status. Certificates replace passwords in EAP-TLS (802.1X and WPA2/WPA3-Enterprise), in IPsec peer authentication with RSA signatures, and for HTTPS servers. Their strength is that the private key never leaves the device and cannot be phished like a password.

Biometrics

Authentication by a physical trait: fingerprint, face, iris or retina, palm, voice. Biometrics are convenient and hard to share, but cannot be changed if compromised, and have error rates: a false acceptance lets the wrong person in, a false rejection keeps the right person out. In practice biometrics usually unlock a possession factor (a phone or laptop's key store) rather than being sent over the network.

Recap

  • Password management: rotation, history/no reuse, password managers, lockout or throttling, change defaults.
  • Length beats complexity; NIST: 15+ characters as a single factor, no composition rules, no forced periodic change, screen against breached lists.
  • MFA = two or more different categories: know, have, are.
  • Certificates: CA-signed X.509 binding of identity to public key, managed by a PKI; used by EAP-TLS and IPsec.
  • Biometrics: something you are; cannot be reset if stolen.

5.5 IPsec remote access and site-to-site VPNs

Another "describe" topic: no configuration is required on the CCNA. You need the two VPN types, the IPsec building blocks with their protocol and port numbers, the difference between tunnel and transport mode, and recognition of GRE over IPsec and DMVPN.

Why VPNs

A VPN carries private traffic across an untrusted network (usually the Internet) while providing the CIA goals: confidentiality (encryption), integrity (a keyed hash detects changes), authentication of the peers, and anti-replay (sequence numbers reject copied packets).

Site-to-site VPN

  • Connects two or more networks through VPN gateways (routers or firewalls) at each site.
  • The tunnel is typically always on (or comes up automatically when matching traffic appears) and is configured by administrators.
  • End hosts are unaware of the VPN: they send normal packets to their default gateway, and the gateway encrypts traffic headed to the other site.
  • Uses IPsec in tunnel mode, because the gateways protect packets on behalf of other hosts.

Remote-access VPN

  • Connects a single user device to the corporate network (teleworkers, travelers).
  • The tunnel is on demand: the user starts it, and VPN client software runs on the device. Cisco's client is Cisco Secure Client (formerly AnyConnect).
  • Two common technologies: TLS (SSL) VPN, running over TLS on TCP 443 (and DTLS over UDP for performance), which passes through almost any firewall; and IPsec with IKEv2. Cisco Secure Client supports both. Some headends also offer a clientless, browser-based portal for limited access to web applications.
  • The headend is usually a firewall (Cisco Secure Firewall ASA or FTD) or a router.

IPsec building blocks

IPsec is a framework (RFC 4301) rather than a single protocol. It combines:

ComponentIdentifierProvides
IKE (Internet Key Exchange), built on ISAKMPUDP 500Authenticates the peers (pre-shared key or RSA certificates), negotiates algorithms, uses Diffie-Hellman to create shared keys, and builds the security associations (SAs)
NAT Traversal (NAT-T)UDP 4500Wraps ESP in UDP when a NAT device is detected between peers, so the NAT can track it by port
ESP (Encapsulating Security Payload)IP protocol 50Confidentiality (encryption), integrity, data origin authentication, anti-replay
AH (Authentication Header)IP protocol 51Integrity, data origin authentication, anti-replay. No encryption. Authenticates the outer IP header too, so it is incompatible with NAT

Within those, IPsec uses interchangeable algorithms for each job, which is why it is called a framework:

  • Encryption (confidentiality): AES (DES and 3DES are obsolete).
  • Integrity/hashing: SHA-2 family HMAC (MD5 and SHA-1 are legacy).
  • Peer authentication: pre-shared key or RSA digital signatures (certificates).
  • Key exchange: Diffie-Hellman groups.

With IKEv1, phase 1 builds a protected management tunnel (the ISAKMP or IKE SA) and phase 2 negotiates the IPsec SAs that carry data. IKEv2 does the same work in fewer messages. IPsec SAs are one-way, so each tunnel uses at least one pair (the IKE SA itself is bidirectional).

Remember: IKE UDP 500, NAT-T UDP 4500, ESP protocol 50 (encrypts), AH protocol 51 (no encryption, breaks with NAT). Real deployments use ESP.

Tunnel mode vs transport mode

  • Tunnel mode: the entire original IP packet, header included, is encrypted and placed behind a new outer IP header that carries the gateway addresses. Used by site-to-site VPNs and the default for Cisco routers.
  • Transport mode: the original IP header is kept and only the payload (TCP/UDP and data) is protected. Used host to host, or to protect a GRE tunnel whose own header already provides the outer addresses.

GRE over IPsec and DMVPN (recognition level)

  • GRE (IP protocol 47) builds a virtual point-to-point tunnel interface that can carry multicast and broadcast, so routing protocols such as OSPF can run across it. GRE alone provides no encryption.
  • A plain IPsec site-to-site tunnel carries only unicast IP. GRE over IPsec combines them: GRE carries the routing protocol and multicast, and IPsec encrypts the GRE packets.
  • DMVPN (Dynamic Multipoint VPN) is a Cisco design for hub-and-spoke networks with many branches. Spokes need only the hub configured, and spoke-to-spoke tunnels are built dynamically on demand. It uses multipoint GRE, NHRP (to find other spokes' public addresses) and IPsec.

Exam trap: If a question asks how to run a routing protocol over an encrypted Internet tunnel, the answer is GRE over IPsec (or DMVPN at scale), not IPsec alone and not GRE alone.

Recap

  • Site-to-site: gateway to gateway, always on, hosts unaware, tunnel mode. Remote access: user device with client (Cisco Secure Client), TLS/DTLS or IPsec IKEv2.
  • IKE UDP 500, NAT-T UDP 4500, ESP protocol 50, AH protocol 51.
  • ESP gives confidentiality + integrity + authentication + anti-replay; AH gives no confidentiality and fails through NAT.
  • Tunnel mode encrypts the whole original packet and adds a new IP header; transport mode keeps the original header.
  • GRE carries multicast/routing protocols but does not encrypt; GRE over IPsec and DMVPN combine both.

5.6 Configure and verify access control lists

ACLs are among the most heavily tested configuration skills on the CCNA. Expect to write an ACL from a requirement, find the error in one, calculate wildcard masks, pick the right interface and direction, and predict whether a given packet is permitted. This section covers IPv4 ACLs in depth and IPv6 ACLs at recognition level only.

How an ACL is processed

  1. An ACL is an ordered list of entries (ACEs), each permit or deny with match conditions.
  2. IOS compares the packet against the entries top down and stops at the first match. That entry's action is applied and no later entry is examined.
  3. If nothing matches, the packet hits the implicit deny any at the end of every ACL. It is invisible in the config and has no counter in show access-lists.

Consequences you must apply on the exam:

  • Put more specific entries above more general ones. A host deny below a subnet permit never matches.
  • An ACL with only deny entries blocks everything (the denies, then the implicit deny).
  • To see how often the implicit deny is hit, add an explicit deny ip any any (optionally with log) at the end; it then has a counter.

Wildcard masks

Worked example: which range does an ACE match?

access-list 10 permit 172.16.40.0 0.0.7.255: the third octet wildcard is 7 (00000111), so the low 3 bits of the third octet are ignored. 40 is 00101000, a multiple of 8, so the range is 172.16.40.0 to 172.16.47.255 (a /21).

A trick question: permit 172.16.42.0 0.0.7.255. The ignored bits of 42 (00101010) do not matter, so IOS rewrites it as 172.16.40.0 0.0.7.255 in the running config and it still matches 40.0 to 47.255. IOS zeroes the "don't care" bits for you; the result may cover more than you intended.

Summarizing several subnets in one entry

Match 192.168.16.0/24 through 192.168.23.0/24: that is 8 consecutive /24s starting at a multiple of 8, so 192.168.16.0 0.0.7.255. If the block does not start on the right boundary (for example 192.168.18.0 to 192.168.25.0), one entry cannot match it exactly; use several.

Odd (non-contiguous) wildcards

Wildcards do not need to be contiguous. 10.1.1.1 0.0.0.254 means: first three octets must be 10.1.1, last bit must be 1, the other 7 bits of the last octet are ignored. It matches every odd address in 10.1.1.0/24. 10.1.1.0 0.0.0.254 matches every even address. 10.0.5.0 0.255.0.255 matches any 10.x.5.y, such as the VLAN 5 subnet in every site of a 10.site.vlan.host scheme. You should be able to read these; you will rarely write them.

Exam trap: access-list 10 permit 10.1.10.0 255.255.255.0 is accepted by IOS but it is a wildcard, not a subnet mask. It ignores the first three octets and requires the last octet to be 0, so it matches 10.1.10.0, 192.168.7.0 and every other address ending in .0, and nothing in the 10.1.10.0/24 host range. A subnet mask in an ACL is almost always a bug.

Extended ACLs

Syntax: access-list 100-199|2000-2699 {permit|deny} protocol source src-wildcard [operator port] destination dst-wildcard [operator port] [established] [log]. In a named extended ACL the same line follows an optional sequence number.

  • Protocol: ip (any IPv4 packet), tcp, udp, icmp, ospf, eigrp, gre, esp, or a protocol number. Port operators are allowed only with tcp and udp.
  • Port position matters: an operator right after the source address matches the source port; right after the destination address it matches the destination port. Client requests go to a well-known destination port, so ... host 192.168.50.10 eq www matches web requests to the server.
  • Operators: eq (equal), neq (not equal), gt (greater than), lt (less than), range low high (inclusive).
  • established (TCP only) matches segments with the ACK or RST bit set, meaning replies within a session someone inside started. A SYN that opens a new connection has no ACK, so it does not match. It is a simple way to let return traffic in without allowing new inbound connections.
  • ICMP can be matched by type: permit icmp any any echo and echo-reply.

Applying ACLs: interface, direction, limits

  • ip access-group {number|name} {in|out} in interface mode applies an ACL to packets routed through that interface.
  • in filters packets arriving on the interface before the routing decision. out filters packets leaving the interface after routing.
  • Only one ACL per interface, per direction, per protocol (one IPv4 in, one IPv4 out, one IPv6 in, one IPv6 out). Applying a second IPv4 ACL in the same direction replaces the first.
  • Outbound ACLs do not filter packets the router itself generates (for example its own pings or routing updates).
  • An interface referencing an ACL that does not exist (or is empty) permits all traffic.
  • Inbound ACLs do filter control-plane traffic arriving on that interface, such as OSPF hellos (protocol 89) and BGP. If you add a final deny, permit routing protocol traffic first, or the neighbor drops.

Placement guidance

  • Extended ACLs: as close to the source as possible. They match source, destination and port precisely, so dropping early saves bandwidth on every later link without collateral damage.
  • Standard ACLs: as close to the destination as possible. They match only the source; placed near the source, they would block that host from every destination behind the interface, not just the one you meant.
  • Choose the direction that catches the traffic once: inbound on the interface where it enters, or outbound on the interface toward the destination.

Entries get sequence numbers 10, 20, 30 by default. In ACL sub-mode you can insert, delete, and renumber without retyping the list. This works for named ACLs and also for numbered ACLs entered as ip access-list standard 10 or ip access-list extended 101.

Securing VTY access with access-class

To control who may Telnet or SSH to the router itself, filter the VTY lines rather than every interface:

R1(config)# access-list 5 remark Management hosts allowed to the VTYs
R1(config)# access-list 5 permit host 10.1.10.10
R1(config)# access-list 5 permit 10.1.99.0 0.0.0.255
R1(config)# line vty 0 4
R1(config-line)# access-class 5 in
R1(config-line)# login local
R1(config-line)# transport input ssh
  • access-class is the line-mode command; ip access-group is the interface command. Mixing them up is a common wrong answer.
  • access-class in works no matter which of the router's IP addresses the client connects to, which is the advantage over interface ACLs.
  • A standard ACL is normal here because only the source matters. access-class out exists too: it limits where users on the router can Telnet/SSH to.
  • Apply it to all VTY lines that exist (0 4 or 0 15) or an attacker just gets a different line.

Find the bug: five worked examples

Bug 1: order

access-list 20 permit 10.1.10.0 0.0.0.255
access-list 20 deny host 10.1.10.11

Goal: block 10.1.10.11, allow the rest of the subnet. The host is matched by line 1 first and permitted; line 2 never matches. Fix: put the host deny first.

Bug 2: direction and placement

R1(config)# interface g0/1
R1(config-if)# ip access-group ENG-TO-SRV out

G0/1 faces the Engineering LAN, so outbound traffic on it is going to Engineering, sourced from the servers. Every entry matches source 10.1.20.0/24, so nothing matches except permit ip any any: the ACL does nothing. Fix: in.

Bug 3: DNS over the wrong transport

permit tcp 10.1.20.0 0.0.0.255 host 192.168.50.10 eq www
permit tcp 10.1.20.0 0.0.0.255 host 192.168.50.10 eq domain
deny ip any any

Web pages by IP work, but name resolution fails because normal DNS queries are UDP 53. Fix: add permit udp ... eq domain.

Bug 4: ports on the wrong side

permit tcp 10.1.20.0 0.0.0.255 eq www host 192.168.50.10

This matches packets whose source port is 80. Client requests use a random high source port and destination port 80, so web requests are not matched. Fix: put eq www after the destination.

Bug 5: the router loses its OSPF neighbor

R1(config)# ip access-list extended WAN-IN
R1(config-ext-nacl)# permit tcp any any established
R1(config-ext-nacl)# deny ip any any
R1(config-ext-nacl)# interface g0/0
R1(config-if)# ip access-group WAN-IN in

OSPF hellos arriving on G0/0 (IP protocol 89) hit the deny, the dead timer expires and the adjacency drops. Fix: add permit ospf any any (or the neighbor's address) above the deny.

These three Catalyst features protect the access layer, where untrusted users plug in. DHCP snooping

How it works

  • Every port is untrusted by default once snooping is on. Mark ports toward legitimate DHCP servers, and uplinks toward the distribution layer, as trusted.
  • On an untrusted port the switch drops DHCP server messages: OFFER, ACK, NAK and LEASEQUERY packets. That alone stops a rogue server.
  • It also drops, on untrusted ports: client messages whose Ethernet source MAC differs from the DHCP client hardware address (chaddr), when MAC verification is on (the default); RELEASE or DECLINE messages for a binding that belongs to a different port (stops an attacker releasing someone else's lease); and packets carrying option 82 or a non-zero relay address (giaddr) arriving on an untrusted port.
  • From the client's DHCP exchange the switch builds the DHCP snooping binding table: client MAC, leased IP, lease time, VLAN and port. DAI and IP Source Guard use this table.
  • Trusted ports are not checked and hosts behind them are not added to the table.

Configuration

SW1(config)# ip dhcp snooping
SW1(config)# ip dhcp snooping vlan 10,20
SW1(config)# no ip dhcp snooping information option
SW1(config)# interface g0/1
SW1(config-if)# description Uplink to R1 / legitimate DHCP
SW1(config-if)# ip dhcp snooping trust
SW1(config-if)# exit
SW1(config)# interface range fa0/1 - 24
SW1(config-if-range)# ip dhcp snooping limit rate 10
  • Two enable commands are needed: ip dhcp snooping globally and ip dhcp snooping vlan for each VLAN. Either alone does nothing.
  • ip dhcp snooping limit rate (packets per second) protects against starvation floods. If an untrusted port exceeds it, the port is err-disabled (recovery cause dhcp-rate-limit). Cisco suggests no more than 100 pps on untrusted ports. Trusted ports have no limit by default.

Option 82 and why the lab config disables it

By default a snooping switch inserts DHCP option 82 (relay agent information: which switch and port the request came from) into client requests, but leaves the gateway address field (giaddr) at 0.0.0.0, because the switch is not a relay agent. A Cisco IOS router acting as DHCP server or relay, receiving such a packet on its interface, treats "option 82 present but giaddr is 0" as invalid and drops it. Symptom: snooping is configured correctly, the uplink is trusted, but clients never get an address.

Fixes, pick one:

  • On the switch: no ip dhcp snooping information option (stop inserting option 82). This is the usual choice in small networks and labs.
  • On the IOS relay or server: ip dhcp relay information trust-all globally (or ip dhcp relay information trusted on the interface) so it accepts the option.

A related command, ip dhcp snooping information option allow-untrusted, is for an aggregation switch that receives already-tagged packets from an edge switch on an untrusted port; recognize it, but know the edge-switch fix above first.

Dynamic ARP Inspection (DAI)

How it works

  • DAI intercepts ARP requests and replies on untrusted ports in the VLANs where it is enabled, and checks the sender's IP-to-MAC pair against the DHCP snooping binding table (or against ARP ACLs for statically addressed hosts). A mismatch is dropped and logged. That stops a host from claiming to be the gateway.
  • Therefore DHCP snooping must be running for DAI to work with DHCP clients.
  • Trusted ports are not inspected. Trust switch uplinks and ports to routers and other devices with static IPs that have no binding (or write an ARP ACL for them). If you forget, the gateway's own ARP replies are dropped and the whole VLAN loses its default gateway.
  • Optional extra checks with ip arp inspection validate: src-mac (Ethernet source MAC equals ARP sender MAC), dst-mac (Ethernet destination MAC equals ARP target MAC, on replies), ip (rejects invalid addresses such as 0.0.0.0, 255.255.255.255 and multicast). Off by default. Each validate command replaces the previous one, so put all keywords on one line.
  • Rate limit: untrusted ports default to 15 ARP packets per second (burst interval 1 second); trusted ports are unlimited. Exceeding the limit err-disables the port (recovery cause arp-inspection).

The three As

Authentication: who are you?
Verifies identity, for example a username and password, a certificate, or a token code. Example: an admin logs in to R1 over SSH with their Active Directory credentials.
Authorization: what are you allowed to do?
Decides which resources or commands an authenticated user may use. Example: the NOC group may run show commands but not enter configuration mode; a wireless user is placed in VLAN 30.
Accounting: what did you do?
Records activity: login and logout times, commands entered, session duration, data used. Example: an audit log shows that admin entered no shutdown on G0/1 at 14:02.

Tip: A bank analogy works well: showing ID is authentication, the teller checking which accounts you may withdraw from is authorization, and the transaction receipt is accounting.

Local versus server-based AAA

  • Local: usernames live on each device (username ... secret with login local, as in 5.3). Simple, works when the network is down, but every change must be made on every device and there is no central accounting.
  • Server-based: devices ask a central AAA server, using TACACS+ or RADIUS. One place to add or remove users, central policy and audit logs. Cisco's server is Cisco Identity Services Engine (ISE), which speaks both protocols.
  • Best practice is server-based with local as the fallback in case the server is unreachable.

  • aaa new-model turns on AAA. From then on, method lists control login and the old line-level password/login commands no longer apply. Create a local user first so you cannot lock yourself out.
  • aaa authentication login default group tacacs+ local is a method list named default: try the TACACS+ servers first, then the local database. It applies to all lines unless a line names another list with login authentication NAME.
  • The next method is tried only if the previous one returns an error (server unreachable or timing out). If the server answers and rejects the password, login fails; it does not fall back to local.
  • Older syntax you may also see: tacacs-server host 10.1.100.20 and tacacs-server key ...; for RADIUS, radius server NAME with address ipv4 ... auth-port 1812 acct-port 1813 or the older radius-server host.

Remember: TACACS+ = TCP 49, whole body protected, separates the three As, per-command control, used for admin access. RADIUS = UDP 1812/1813, only the password hidden, combines authentication and authorization, used for network access and 802.1X.

802.1X port-based network access control

  • Supplicant: the client device and its 802.1X software, requesting access.
  • Authenticator: the switch (wired) or WLC/AP (wireless). It blocks the port, relays authentication messages, and opens the port (and can assign a VLAN or ACL) when the server says yes.
  • Authentication server: a RADIUS server such as Cisco ISE that checks the credentials and returns accept or reject plus authorization attributes.
  • EAP (Extensible Authentication Protocol) is the framework that carries the actual method (EAP-TLS, PEAP and others, covered in 5.9). Between supplicant and authenticator it travels as EAPOL frames directly over Ethernet or Wi-Fi (the client has no IP yet). Between authenticator and server it travels inside RADIUS.

Exam trap: The switch is the authenticator, not the authentication server. And 802.1X uses RADIUS, not TACACS+, to reach the server.

5.9 Wireless security protocols (WPA, WPA2, WPA3)

Wireless frames reach anyone in range, so Wi-Fi security must provide authentication (who may join), encryption (confidentiality) and message integrity. Know each generation's cipher and integrity mechanism, Personal versus Enterprise modes, and the improvements in WPA3.

The generations

Remember: WEP = RC4, broken. WPA = TKIP + MIC. WPA2 = AES-CCMP (802.11i). WPA3 = SAE, mandatory PMF, forward secrecy, GCMP-256 in 192-bit mode.

Personal versus Enterprise

  • Personal mode: every user shares one passphrase. WPA and WPA2 Personal use a PSK (pre-shared key); WPA3 Personal uses SAE. Simple, but the key is shared, so removing one user means changing it for everyone, and logs cannot identify individuals.
  • Enterprise mode: each user or device authenticates individually with 802.1X/EAP to a RADIUS server (for example Cisco ISE), and each session gets its own keys. The roles from 5.8 apply: the client is the supplicant, the WLC (or AP) is the authenticator.

The 4-way handshake

Both modes end with a pairwise master key (PMK) that the client and AP share: in Personal mode it is derived from the passphrase and SSID; in Enterprise mode it comes from the 802.1X/EAP exchange. The AP and client then run the 4-way handshake: they exchange random numbers (ANonce and SNonce), each derives the pairwise transient key (PTK) used to encrypt unicast traffic, they prove to each other that they hold the same PMK, and the AP delivers the group temporal key (GTK) for broadcast and multicast. The PMK itself is never sent over the air.

The weakness in WPA2-Personal: anyone who captures one handshake can run an offline dictionary attack against the passphrase, because the handshake lets them test guesses. That is why short PSKs are dangerous, and what SAE fixes.

WPA3 improvements

  • SAE (Simultaneous Authentication of Equals) replaces PSK in WPA3-Personal. It is a password-authenticated key exchange: each guess requires a live exchange with the AP, so offline dictionary attacks do not work.
  • Forward secrecy: each session key is independent, so capturing traffic today and learning the password later does not decrypt the old traffic.
  • Protected Management Frames (PMF, 802.11w) are mandatory, which blocks forged deauthentication and disassociation frames.
  • WPA3-Enterprise 192-bit mode (CNSA/Suite B) uses GCMP-256 and stronger hashing for high-security environments.
  • Transition mode lets WPA2 (PSK) and WPA3 (SAE) clients share one SSID during migration.
  • Enhanced Open (OWE, Opportunistic Wireless Encryption) is a companion standard, not WPA3 itself: an open network with no password, where each client still gets individual encryption from a Diffie-Hellman exchange. It suits cafes and guest networks.

Recap

  • WEP (RC4) is broken; WPA used TKIP and MIC; WPA2 uses AES-CCMP from 802.11i; WPA3 adds SAE, mandatory PMF and forward secrecy, with GCMP-256 in 192-bit Enterprise mode.
  • Personal = shared key (PSK in WPA2, SAE in WPA3). Enterprise = 802.1X/EAP with a RADIUS server.
  • The 4-way handshake derives the PTK and delivers the GTK from the PMK, which is never transmitted.
  • WPA2-PSK handshakes can be cracked offline; SAE prevents that.
  • OWE (Enhanced Open) encrypts open networks without a password. EAP-TLS uses certificates on both sides; PEAP uses only a server certificate.

AireOS WLC: step by step

  1. Prerequisite: a dynamic interface for the client VLAN. Under Controller > Interfaces > New, give a name and VLAN ID, then an IP address, mask, gateway, physical port and DHCP server for that VLAN. The WLAN will be mapped to this interface, which decides which VLAN clients land in. (In a small lab you can map the WLAN to the management interface instead.)
  2. WLANs tab, choose Create New from the drop-down, click Go.
  3. On WLANs > New: Type WLAN, Profile Name (unique, up to 32 characters, used internally), SSID (up to 32 characters, what clients see), ID (the WLAN ID number). Click Apply; the WLANs > Edit page opens.
  4. General tab: tick Status: Enabled (a new WLAN is not active until you do), choose the Interface/Interface Group(G) (the dynamic interface from step 1), check Radio Policy (all bands or specific ones) and leave Broadcast SSID ticked.
  5. Security tab, Layer 2 sub-tab: Layer 2 Security = WPA+WPA2. Under WPA+WPA2 Parameters tick WPA2 Policy and WPA2 Encryption: AES (leave WPA Policy and TKIP unticked). Under Authentication Key Management, tick PSK and untick 802.1X (802.1X is the default key management on a new WLAN). Set PSK Format to ASCII and type the passphrase.
  6. Check Layer 3 security is None (no web authentication) unless you want a portal.
  7. Click Apply, then Save Configuration (top right) so it survives a reboot.
